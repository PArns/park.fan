# The page render is the bigger half of the API budget, and it was never audited (ANTI-PATTERN)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

the projection rule above was written for the five-minute poll and applied only there. The other copy of the same data — the one React serializes into `self.__next_f.push(…)` so the client can hydrate — is paid by **every request including the crawler's**, is never re-fetched, and had never been measured. It is roughly half the bytes of these pages: 199 KB of a park calendar's 444 KB, 205 KB of a park page's 500 KB. Three holes, all found by weighing the payload rather than reading the code. **A page that renders none of a thing must not ship it**: the wait-time calendar draws no attraction cards, and the only readers of `park.attractions` on that route are `ParkTodayPanel`'s headliner rows and `useParkTileItems`'s land count — between them **twelve fields, against the twenty-two it was shipping**, so `bestVisitTimes` (9.74 KB), `statistics` (5.07 KB) and `ropeDrop` (4.52 KB) rode along for forty rides nobody drew. `leanParkForCalendarShell` is an **allow**-list, not a `delete` chain like its siblings, because the kept set is the short one and a field the API adds next month then stays out by default: the list goes 39.3 → 15.2 KB, the page **−28.6 KB of HTML and −1.52 KB brotli (−2.9 %)**. **Judge it compressed and A/B it in one build**: the raw figure flatters this by 19×, brotli eats repeated JSON keys for breakfast, and the first estimate — taken by diffing a local render against a production one — read −3.2 KB because the two deploys differed for reasons that had nothing to do with the change. Rebuild both sides through the same pipeline, or the re-chunking is what you measured. **A rule written down is not a rule applied**: `comparison` and `baseline` are named in the block above as never rendered, `leanParkForLivePoll` duly omits them, and `leanParkForShell` — the server half — shipped them on every attraction of every park page for as long as both have existed (`ComparisonBadge` is real, and is wired to nothing outside `/ui`, where it is fed string literals). **And a translation namespace is as coarse as its widest consumer**: `parks` is 15.1 KB and arrives whole because 23 client components ask for `useTranslations('parks')`, so a ride page pays 3.18 KB of `parks.calendarPage` for a page with no calendar, plus `calendarView`, `bestDays`, `dayDetail` and `seasons`. Narrowing those 23 call sites to the sub-namespaces the routed map already supports (`parks.crowdLevels` and `parks.status` prove the mechanism) is worth **−3.0 KB brotli, −5.7 %** on the highest-invocation route in the app — twice the calendar trim, and the largest single item left; it is not done, because next-intl answers a missing namespace by logging MISSING_MESSAGE and rendering the raw key, so it is 23 chances to ship a visible one and wants `pnpm check:client-messages` green at each step. Restaurants are the other unclaimed 6.6 KB, held up by a component contract rather than by bytes: `useParkTileItems` reads forty-six full records for a `.length` and an `OPERATING` count, and inventing a `ParkRestaurant` with an empty `name` to satisfy the type puts a lie one render from a reader. **What makes all three expensive is which routes they land on, and it is not the popular ones.** Twelve hours of production: the park page took 1.7 K invocations, 3 min CPU, 101 MB — the **calendar** took 9.9 K / 26 min / 567 MB and the **ride page** 11 K / 22 min / 491 MB. Both are `force-dynamic`, so every origin miss is a render, and they are the two highest-cardinality routes in the site (212 parks × 22 months × 6 locales = 27,984 calendar URLs, 42,756 attraction URLs). A crawler walking a sitemap misses the CDN once per URL per TTL — each calendar URL is fetched about **0.7 times a day** and each ride URL about **0.5**, which is a daily sweep and not a cache that could ever be warm — so **cost follows the URL count, not the visitor count**, and the audit has to start from the invocation table rather than from what feels busy. It also bounds what trimming can win: a page-weight cut moves transfer and a little CPU, while the 71,000-URL crawl surface is what sets the number of renders, and only a product decision about the twenty-two-month calendar span moves that. **Measure it, do not reason about it**, and measure it on a **cache-busted** URL: `curl -H 'Accept-Encoding: identity' 'https://park.fan/…?cb=$RANDOM'`, join the `self.__next_f.push([1,"…"])` string literals, then size each field and brotli-diff the before and after. A plain fetch returns whatever Cloudflare is holding — a `cf-cache-status: HIT` copy of the park page showed `statistics` and `bestVisitTimes` absent from its attractions and a fresh render of the same URL had both, which reads exactly like a projection that is already working.
