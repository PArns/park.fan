# Design and layout rules

These are the standing rules for this area, moved out of `CLAUDE.md` so that a session reads an index first and opens only the pages its task needs. The wording is unchanged; each rule links on to the document that carries the measurements behind it.

## A chapter opens the same way everywhere (REQUIREMENT)

one component draws every chapter header on the site — `ChapterHeading` (`components/common/chapter-heading.tsx`): oversized translucent glyph, optional kicker, title, closing rule. The guide page reaches it through `SectionShell`, a blog post's `##` through the h2 renderer in `blog-content.tsx`, ride pages through `PageSection` → `SectionHeading`, park pages directly. There were **five** before, three of them on one park page — `text-xl font-semibold` with an icon, `text-xl font-bold` with an icon, a `text-2xl` frosted pill, a bare `<h2 class="text-xl font-bold">`, `GlassSectionTitle` — and nothing told a reader which of them opened a chapter and which labelled a card inside one. `GlassSectionTitle` stays, for the band _inside_ a page (homepage favourites, the nearby-parks list): it is not a chapter header. Three decisions sit in the component so a call site cannot get them wrong. **A number must not skip:** a post's chapter numbers come from `extractToc(markdown)` and never from a counter incremented while rendering, because the body is split into one `<ReactMarkdown>` per widget fence and a render-time counter restarts at each one (01, 02, 01, 02); park and ride chapters carry **no** number for the same reason, since `NearbyParksSection` renders nothing for 48 % of parks. **An icon standing in for the number is drawn at `/25`, not `/15`** — the numeral is solid and survives 15 %, a hairline Lucide icon disappears. **`frosted` is a full-width band, not a `w-fit` pill**, because park and ride pages sit on an arbitrary photo and a watermark over the bright part of one is unreadable; the heading's own `border-b` is the band's lower edge. And the height moves when a title wraps, per locale and per breakpoint, so both streamed chapters render the **real** heading while loading — `ParkBestDaysHeader` and `ParkStatsHeader` exist as their own files so the placeholder can mount them with only the data-dependent hint replaced by a `Skeleton`. `SectionHeading`'s `plain` variant is unchanged and is still what belongs **inside** a card. See [design system → chapter headings](docs/design/design-system.md#chapter-headings).

## A client-only preference may not decide server-rendered markup (REQUIREMENT)

the °C/°F pick lives in a cookie and the visitor's locale, the pages are statically cached, so temperatures are server-rendered in **both** units and an inline script sets `html[data-temp-unit]` before paint with CSS showing one (`.u-metric`/`.u-imperial`). The toggle itself branched on the value during render, and that is not a flash bug but a hydration bug: **hydration is not one pass**, boundaries commit separately, so the provider had already resolved the unit to `F` while a weather widget further down the article was still waiting to hydrate — React logged the subtree and **patched nothing**, leaving the wrong value on screen. Express it in CSS where you can: the header's °C/°F button draws its own label off the very `.u-metric`/`.u-imperial` pair the values use — it renders both and the attribute picks one, so a static class cannot mismatch and there is no pressed state to report (its click reads `data-temp-unit` off the document, never the context, so what it flips is by definition what the reader is looking at). Where you cannot, the guard is **local to the consumer** — `aria-pressed` waits for the component's own mount, because fixing the provider does not reach it: `useSyncExternalStore`'s server snapshot covers the hook's own hydration render, not a consumer that hydrates after the provider re-rendered. See [conventions](docs/development/conventions.md#15-a-client-only-preference-may-not-decide-server-rendered-markup).

## A cell is gated on its content, and a component that fills one may not return `null` — nor one line (REQUIREMENT)

the ride page's „Beste Besuchszeit planen" grid counts its columns from `attraction.ropeDrop && typicalWaits?.displayable` — one level above `RopeDropCard`, which answered `null` for its negative case (not worth a rope drop, not an evening ride, and no neighbour in the park carrying a recommendation either, so the muted „no need to rush" note had nothing to contrast against). The cell, its hairline and a second column were drawn around nothing: measured over all 213 parks, **183 ride pages with a visibly empty half** plus 159 more showing an empty box under the chapter heading, because **60 parks carry no rope-drop recommendation at all** — every Efteling ride that has one is in that set, which is how it was reported. The fix is not a third condition at the call site, which is a second copy of the card's own logic free to drift from it, but making the component **total**: `ropeDropCardVariant()` resolves every recommendation to one of three panels and `RopeDropCard` returns `React.ReactElement`, so the next `return null` is a compiler error. Where a component genuinely may render nothing, export the predicate it uses itself and let the count and the cell ask the same question. **An element is not the bar — filling the cell with one line is the same bug one size smaller**, and it was the larger half: where the park DID carry recommendations, that note rendered alone in half a card beside a full chart, on **470 ride pages in 87 parks** (measured 2026-09-15) against the 183 the `null` cost. The note stays, because the contrast to a recommended neighbour is real information, but it is a **footer inside the stand-in panel** rather than a panel of its own, under the same single hairline as the low-confidence hint — so `parkHasRecommendations` is a footer detail and never a branch, and the ride gets the readings it always had (312 of those 470 print the quietest-weekday sentence, 66 %, against 209 of 377 for the rides that reach the panel on their own). **And moving a sentence changes what it claims, because its neighbours change**: it read „die Wartezeiten bleiben über den Tag überschaubar (ca. {openWait} Min. zur Öffnung)", which survives alone in half a card and not above three tiles — the bracket is a third copy of the wait at opening, and „überschaubar" is contradicted outright on **65 of the 470** (peak ≥ 60 min, 7 of them ≥ 90), up to Tokyo DisneySeas Soaring at 140 to 180. The footer keeps only what the branch knows, `worth === false` plus the contrast, and leaves the size of the queue to the tiles that measured it; the contrast may name the park's other rides because **zero** parks holding one of those 470 recommend only evenings. Rewritten in all six locales. The stand-in panel then has to earn the chapter's heading, and **what it may say is a measurement rather than a design**: over those 183 rides the quietest hour is defensible on **15** (146 carry a trough equal to the wait at opening), the quietest weekday on **119** (`quietestWeekdays` drops a thinly measured day rather than refusing and names both days of a tie, like the best-travel-time hub one grain coarser; 61 more read as a flat week, and 3 stay silent rather than name a day while a dropped thin day draws the shorter bar right beside the sentence — „no weekday stands out“ is a measurement and may only be printed where the week was measured), and `busyPeak − openWait` on all 183, median 25 minutes. It carries no sentence explaining the missing recommendation: that threshold lives in the backend, this repo cannot cite it, and an invented reason reads as measured to whoever finds it next. Same card, one more rule: **one colour rank, in every place a number appears** — the summary tiles said blue = Voll while the bars and legend said blue = Normal. The tiles carry the rank as the legend's own **swatch** rather than by tinting the digits, because `text-primary` is 3.47 : 1 on the light card and `text-lg font-semibold` is 18 px at 600, i.e. not WCAG „large text" and owing 4.5 — a swatch owes 3, which the same colour clears, and both figures keep a text-grade contrast. And **a wash is not a boundary**: `bg-primary/25` over the `bg-muted/40` track computes to **1.32 : 1** in light and 1.40 : 1 in dark, which is why the bar looked like it ended at the Normal value with the Voll number floating above it, and no opacity fixes it — the light track is rgb(251,251,251) and `bg-primary` itself only reaches 3.36 : 1 against it, so no third tone clears 3 : 1 from both the track and the solid segment. A boundary that must be seen is a **line**: a solid `bg-primary` top rule (3.36 : 1 light, 5.24 : 1 dark). Printing „typical–busy" above each bar instead was rejected on a count, not a hunch — 217 of the catalogue's 5,942 ride-days round to seven characters, ~40 px in a ~36 px column at 360 px, and the seven columns are `flex-1` so the row runs past the card rather than wrapping. **And the rank cannot name that number**, which the code claimed it did („the Voll value, in the Voll tone"): `text-muted-foreground` is `lab(66.13 0 0)` dark and `lab(48.50 0 0)` light, i.e. **achromatic**, so it sits outside a rank whose two members are a solid accent and a washed one — and the `title` carrying the pair predates the change and is unreachable on a phone. The row gets a caption of its own instead (the legend's Voll swatch plus „Zahlen: Voll"), with the swatch rather than the word alone because a lone label at the left edge of a seven-column row reads as the first column's. `pnpm test:typical-waits`. See [design system → the ride page is the park page's anatomy](docs/design/design-system.md#the-ride-page-is-the-park-pages-anatomy).

## Reuse existing components (REQUIREMENT)

always reuse existing components (e.g. `ParkStatusBadge`, `CrowdLevelBadge`, `Badge`, `ParkCard`) instead of re-implementing UI inline — keeps styling/colors consistent. Only build new when nothing suitable exists. See [conventions](docs/development/conventions.md#11-reuse-existing-components).

## The header is 48 px, and its height is written down in four places (REQUIREMENT)

`h-12` on `<header>` (the inner container is `h-full`, never a second copy of the number), the `<Suspense>` fallback in `app/[locale]/layout.tsx` that reserves the bar while the client `Header` streams in, and `-mt-12` on the three heroes it floats over (homepage, blog post banner, editorial hero). Miss the fallback and every page opens with a shift of the difference. Control heights come off the button scale in `components/ui/button.tsx` (`sm` 32 / default 36 / `lg` 40), not out of the air — the old bar put the **largest** of them, the 40 px `lg` search field, in the shortest row in the app at 71 % of a 56 px bar. That scale now has a **phone tier**: below `sm`, `sm`/`default`/`icon`/`icon-sm` all resolve to **44 px**, which is the number `app/admin/_ui/controls.tsx` and `globals.css`'s `.touch-target` had both already written down and neither had ever applied outside `/admin` — `.touch-target` was on **nothing at all**, and a grep for `min-h-11|h-11|touch-manipulation` over `components/` + `app/[locale]` returned five hits, none of them a control. The bar is the **one** documented exception, because 44 in 48 is the same mistake one size worse: `LocaleSwitcher` (`max-sm:h-8`), the `sm` branch of `search-bar.tsx` (`max-sm:h-9 max-sm:w-9`) and the burger (`max-sm:size-9`) cancel it at their own call site and name the requirement. Cancel it nowhere else without one. What stays open is about this bar and not about those classes — the 32 px locale switcher and the 28 px theme toggle sit 4 px apart in a row with no room to grow, so the answer there is the bar's height, i.e. the number in all four places, not the button's. **The width is written down nowhere and is 25 px**, which is what the third preference control cost: measured at 360 px the row carries 303 px in 328 (lockup 107, search 36, locale 56, theme 48, burger 36, 20 of gaps), the same to within 6 px in all six languages because nothing in it is prose. So the °C/°F control — moved out of the weather card, where it only ever reached park pages — is **one button showing the ACTIVE unit**, 28 px and 24 on a phone, not a 54 px `°C | °F` pill and not a 21.5 px bare text button either (both overflow once the gap is counted); it takes the theme switch's `h-7` and ring so the two read as a pair, and it looks the same above `sm` rather than growing a second markup. **Its width may not depend on which unit is active**, which is what sizing it by its label got wrong: `°F` is narrower than `°C`, so the button changed width under the finger that pressed it and slid its neighbours over with it, in a row where every pixel is spoken for. `min-w-7` / `max-sm:min-w-6` with `px-1` fixes the box at 28 and 24 — the label is ~13 px and irrelevant while it is under that, and the padding is what happens if a reader's font ever pushes past it. Those 28 px came from three places, none of them a control's height: the **locale switcher's country code** (22 px, `max-sm:hidden` — a flag that already says it, in front of a dropdown listing code and language name), the two **gaps between the action groups** (`max-sm:gap-1`, 8 px) and the button's own phone tier (`max-sm:min-w-6`, 4 px). Measured after at 320/360/390 px × six locales: 301 px used, 27 px slack at 360 — two pixels _less_ than before the button existed — identical in every language, and the button's box and its neighbours' positions unchanged to 0.0 px across a toggle in either direction. **320 px is the width that decides the last two savings**: the narrowest viewport in the logs, already 15 px over its box before any of this and invisible because the container's `px-4` swallowed it; the button alone took it to 26 over and scrolled the document to 330. It is 13 over now, inside the padding, document = viewport from 320 to 768. There is no room for a fourth preference: the next one is a question about the bar's height or about a preferences sheet. **And its breakpoints ask the BAR's width, not the window's** — `@container` on the `<header>`, `@min-[1024px]:` and `@min-[1280px]:` on the four switches inside it. The two numbers used to be the same thing and stopped being it when the trip planner's panel started insetting the page: with a 448 px panel on a 1440 px window the bar's box is 992 px while `lg:`/`xl:` still read 1440, so it kept laying out a desktop's worth of content in three quarters of the room — children summing 1087.9 px in 992, the °C/°F toggle and the theme switch 95.9 px **under** the panel in German and 171.1 in French, and worse the smaller the window (+255.9 at 1280, +389.7 at 1024). On the header and **not** on the `container mx-auto` row inside it: `container-type` makes an element the containing block for absolutely positioned descendants, and the corner logo is `absolute left-6` — against the row it would sit 80 px further right and break the very handoff described below. `container-type: inline-size` implies `contain: layout style inline-size` and **not** `contain: paint`, so it does not make the header a backdrop root; the menu band's blur is unchanged, measured. The thresholds are the old ones on purpose: with the planner shut the header spans the viewport, so the same two numbers are the same two switches at the same two window widths and every existing layout is untouched. The other half is a **cap on the panel** (`PAGE_MIN_PX = 360` in `lib/planner/panel-width.ts`, applied in `getSnapshot` so the panel, the page's inset and the edge tab cannot disagree): at 768 px the stored 448 becomes 408, because below 360 px of page the bar starts sliding under again whatever its breakpoints say. Measured after, at 1440/1280/1024/900/768 × de and fr: **0.0 px overhang in all ten**. And the logo is **one component rendered twice**, never two sets of classes: on a hero page the header parks a copy in the corner and keeps one in the flex flow, then cross-fades them while sliding one onto the other, which only reads as a single object if they are congruent. They were not — `h-7 md:h-9`+`h-5 md:h-6`+`gap-0.5` against `h-6`+`h-5`+`gap-1` made the handoff animate a 1.5× scale, and no single factor can reconcile a pin:wordmark ratio of 36:24 with 24:20, so the corner copy stayed 15–25 px wider than the bar copy the whole way across (measured at 1440). `BrandLockup` is the fix and the guarantee: `logoScale` resolves to 1.000, the handoff is a pure translate, and per-frame sampling puts the two boxes 0.0 px apart on all four edges. **And a height has to be the mark's height, not a box it sits somewhere inside**: all four lockup files were exports with the artboard's margin baked in — the pin filled 86.3 % of a 144×144 viewBox vertically and 62.5 % of it horizontally, the wordmark 78.1 % of a 2304×657 one — so `h-6` painted a **20.7 px** pin and `h-5` a **15.6 px** wordmark, a lockup on 43 % of a 48 px bar while every number in the component said 50 %, with a fifth of the device pixels the layout had already reserved going to transparent artwork. It reads as a raster on a 1× display and is invisible from the call site, which is how it survived a rewrite that measured everything else about this bar. The viewBox of all four is the **measured ink box** now (rendered at 6000 px, alpha walked: `fill = 100.00 %`, offset 0.00), the header is pin **26** / wordmark **19** / `gap-2` — the 1.37 between them is the ratio the padded files rendered — and the three other consumers (`theme-wipe`, whose `gap:0` existed _because_ the pin carried ~19 % of its own width as margin, the coaster watermark, the footer) carry the same numbers explicitly and keep the size they had. Cropping alone sharpens nothing: 20.7 px of ink is 20.7 px of ink whatever box is drawn around it. It is what lets the size be raised without a magic number at every call site. `logo-big*.svg` is **not** cropped and must not be: it is the lockup including the wordmark under the pin, which `generate-icons` finds by looking for the widest empty row band. `logo.svg`/`logo-dark.svg` — the detailed pin the footer draws — were the last raster in the set, a 1563×1116 PNG in an SVG wrapper at 77 KB each, and nothing was visibly wrong with them at the 32/48 px the footer asks for, which is precisely why they lasted: a raster with enough resolution for today's largest call site fails silently the first time somebody draws it bigger. They are **cut from the lockup** now by `generate-brand-pin.mjs` (6.2 KB each, −142 KB), and generated rather than hand-exported because the pin would otherwise be one drawing stored twice with nothing comparing them — `pnpm check:brand-pin` is what notices. The split is the exporter's own: Affinity names the halves `<g id="park.fan">` and `<g id="Icon">`, so the wordmark goes by id rather than by hunting an empty band, and `_Linear1` (its green dot) is dropped with it. Ink AR 0.8201 against the raster's 0.8202 is how you know it is the same drawing. The `.png` twins keep the old padded geometry, which is what `lib/og/brand-mark.tsx` and `lib/three/park-scene.ts` have hard-coded. **And the bar's two states may not decide whether the navigation exists**, which is what `isTransparent` did on all six hero pages: `opacity-0 pointer-events-none` on the nav row, the search trigger and the burger, `aria-hidden` on the `<nav>`, `tabIndex={-1}` on every link in it and a `disabled` that also refused to open the panels — so until 50 px of scroll the menu was unclickable, untabbable and out of the accessibility tree, with nothing on screen saying there was one (24 of 24 measured combinations). Two things come with the fix and both are contrast rather than taste. The **scrim is its own layer**: a `background/85` gradient flat over the bar's 48 px and fading out across 32 px below it, as a SECOND absolutely positioned layer rather than a second class list on the material — a gradient is `background-image` and a flat tint is `background-color`, so one layer would drop the scrim the instant the threshold is crossed while the solid colour fades in behind it over 500 ms; two layers cross-fade on `opacity`, which interpolates. Neither may become a `backdrop-filter` or a transform on the `<header>` itself. And the **ink switches with it**: `--muted-foreground` is 4.73 : 1 on `--background`, i.e. 0.23 over the line, so 15 % of a dark photo through the scrim reads 3.3 : 1 — the floating bar runs the nav at `foreground/90` (worst measured 13.31 : 1 against 1.01 : 1 for muted ink on an untinted hero) and it switches with the state and waits for nothing: the two layers' sum runs 85 % → ~65 % → 80 % across the cross-fade, i.e. never far from the 80 % the solid bar has always given muted ink while a hero is still behind it. A `delay-300` on the solid class list was the first fix and is the wrong one — `transition-delay` is one property and the hover rule shares it, so it delays the hover of all seven entries by 300 ms on every page in the app; a timer in state is a `setState` in an effect, which the lint rule refuses. The corner pill holding a second copy of the three preference controls is gone with it — visible search and burger draw exactly where it hung (360 px: pill 240–336 against burger 308–344) — and so is the header's GSAP stagger, whose `fromTo(y: -10 → 0)` is **reversed** on the way back up and only invisible while the row is `opacity-0`. See [design system → header geometry](docs/design/design-system.md#header-geometry).

research the real-world reference **first**, then implement; and **verify every animation from all camera perspectives** (coaster player: Front, Follow, Onboard) across the whole timeline and both day/night themes via the headless render harness (`node scripts/render-coaster-elements.mjs`) before shipping — a green build is not enough. ## The quietest weekday may be two days, and a thin day drops out rather than ending the vote (REQUIREMENT)

the best-travel-time hub showed an em dash for **3 of 6** featured parks, correctly by the old rules and wrongly all the same. A weekday measured far more rarely than the others used to refuse the whole park — Movie Park has 13 Mondays against 23 Sundays — when dropping that one day leaves four comparable ones that do say something; and a tie counted as "cannot choose" when Disneyland Paris measuring 32 minutes on Sunday **and** Wednesday means the park has two quiet days, not none. Both days are named now. Measured across the eighteen parks this table is ever asked about: **12/18 filled → 17/18**, with no park that already had an answer getting a different one. Three refusals remain and each fired on a real park: fewer than four evenly-measured weekdays left, three or more days sharing the minimum (Disney Adventure World reads 39 on four of them — a park with no quiet day), and a "quietest" day not actually below the park's own median. In the same card the **park name is never the cell that gives way**: `table-layout: auto` hands width to the widest unbreakable content, so `max-w-0` on the park column collapsed it to "Europa-P…" while "34 Min. · Voltron Nevera powered by Rimac" kept all 39 characters. The name is the row's subject, a ride name a detail of one column — `w-full max-w-0` moved to the longest-queue cell instead. Same trap one layer over in `RideWaitTable`: the ride column may only claim the slack when it is the **only** text column, or park and type collapse to "Ph… Mult…" beside 500 px of empty name column.

## Blog spotlight cards

`ParkCard`/`AttractionCard` lay out via `row-span-3` + `grid-template-rows: subgrid`, so the row template must sit **on the card itself**, never on a shared wrapper that also holds the heading — `auto` tracks collapse against the panels' `-mb-4`/`-mt-4` and slice the title and wait time. Use `grid [grid-template-rows:auto_2rem_auto] sm:[grid-template-rows:auto_minmax(220px,1fr)_auto]`; the `2rem` absorbs that overlap once the photo is hidden below `sm`, and `minmax(220px,1fr)` keeps image-less cards full height.

## A blog card is a row on phones (REQUIREMENT)

park, ride and blog cards are one object — a photo under two sheets of frosted glass — and all three drop the photo below `sm`. A park card collapsing onto its panels still says everything it has to say; a post card says a title and a date in ~200 px, with the cover it was chosen for hidden and the `-mb-4`/`-mt-4` that were meant to lay the panels over the picture overlapping **each other** by 32 px, so the panel below paints over the last line of the excerpt. So below `sm` the card is not rendered at all: `BlogPostRow` is (`sm:hidden` / `hidden sm:grid`), which is the `compact` variant the homepage's lead column already used. It gets **no variants of its own** — the first version had two, a border and a three-line title where the row replaced a card against an `-mx-2` bleed and two lines where it sat in a list, and on the homepage the two meet (below `lg` the lead post is a row and so are the four under it), so the lead came out inset by 8 px, boxed, and carrying a reading time its neighbours did not have. The **gap** is the same decision one level out: the grids holding these cards were spaced for cards (`gap-4`–`gap-6`), which reads as a stack of separate blocks rather than one list, so all of them drop to `gap-2` below `sm` and keep their own spacing above it — including **both** halves of `LatestBlogSection`'s `lead`, whose two gaps have to agree or the lead detaches from its list. Three more things are load-bearing. It is **two markups, not one responsive tree**, because the glass is a block of inline styles and no breakpoint switches an inline style off — the alternative was moving the park and ride panels into CSS with it. Both photo layers of the hidden card claim **`96px`** for the phone segment of their `sizes`, which is what the row beside them actually paints: left at `100vw` a card marked `priority` (the first in `BlogPostGrid`) preloaded a full-width cover for a `display:none` element, and matching the row means both pick the same srcset candidate, one request instead of two. And the thumbnail carries the card's `objectPosition`, so a focal point tuned in the admin holds at 96 × 64. The **article page** pays the same kind of bill one screen down: the banner's `pt-32` is clearance for the floating header and frames nothing (the banner is content-driven at 642 px against a 490 px `min-h`), so it halves below `sm`, and the table of contents is `hidden lg:block` — in a sidebar it is navigation, on a phone it was **998 px** of chapter links between the breadcrumb and the first sentence, on every post. Together with 16 px off the space above the 30 px breadcrumb pill, the first word moves from 782 px to 698 px. The trade is real and worth revisiting: a phone reader can no longer jump between chapters. The **five full-bleed heroes** (`relative isolate -mt-12 flex min-h-[Nvh] items-end overflow-hidden`: the guide at 86vh, Fancast, the best-travel-time hub and the blog index at 78vh through the shared `Hero`, the blog article at 58vh) each spent a phone's whole first screen on one picture and a title. Below `sm` the headline moves to the **top** and the page pulls its own first section up over the lower part of the photo — the image keeps every pixel and usually gets taller. First content at 390 px: guide 782 → 550, Fancast 722 → 533, best time 714 → 553, index 658 → 482, article 594 → 554. The shared `Hero` takes it as a `flowInto` prop (three callers); `GuideHero` and `BlogPostBanner` are one page each and carry it directly. Two things make it hold: the upward tint gets its mirror over the top third, because the headline would otherwise land on the one barely-tinted part of the photo; and the overlap is **safe by construction** — `HERO_FLOW_INTO_PULL` (176 px) pairs with the hero's mobile `pb-48` (192 px) and **the padding must stay larger than the pull**, so a long headline grows the `max(78vh, content + padding)` hero and carries the pulled-up section down with it. Hand-tuned it was wrong at once: at 360 px the German tagline ran 10 px past the first card while French had 117 px spare; by construction the minimum over six locales × four widths is 16 px. See [design system → the blog card is a row on phones](docs/design/design-system.md#the-blog-card-is-a-row-on-phones).
