# Architecture rules

These are the standing rules for this area, moved out of `CLAUDE.md` so that a session reads an index first and opens only the pages its task needs. The wording is unchanged; each rule links on to the document that carries the measurements behind it.

## Park page loading priority (REQUIREMENT)

the best-travel-time data (best-days calendar + historical stats) must **always load last** — live status, wait times and all weather queries load first. Enforced via `useLoadLast` (`lib/hooks/use-load-last.ts`); see [system-overview](docs/architecture/system-overview.md#4-park-page-loading-priority-requirement).

## A streamed section owes the page its height (REQUIREMENT)

the park page buys TTFB by streaming its slow parts, and the bill arrives as CLS — charged to whatever the visitor is looking at when the boundary resolves. So a `<Suspense>` fallback must reserve the height its content will take. `fallback={null}` is honest only when nothing renders below it: the blog section had one and did **no async work at all** (`hasPublishedPosts`/`getPostsForPark` read the generated manifest synchronously, the lone `await getTranslations` hits messages the render already holds), so the boundary deferred nothing and dropped 467 px of content out of thin air — synchronous data belongs inline, in the first HTML, at full height. And a fallback should render whatever needs **no** data rather than a grey box shaped like it: the best-days header is data-free and its height depends on how the park name wraps (one line on desktop, two on a phone), which sized `Skeleton` blocks were 66–120 px short of until the fallback started rendering the real `ParkBestDaysHeader`. Measure the three states a visitor can observe — fallback, server seed, settled queries — and diff the block geometry; that delta _is_ the shift, and seed → settled measures 0, so the client queries were never it. And on a **prerendered** route a boundary defers nothing whatsoever: the project runs no PPR, so the prerender waits for it anyway and the resolved markup already sits in the shipped `.html`, sorted to the end of the byte stream in a `<div hidden id="S:1">` and grafted in by the `$RC()` after it — which is how the glossary term page dropped 396–1463 px into the column two seconds after paint and pushed the "back to dictionary" button (`div.pb-2`, the element Cloudflare names) down with everything under it. The client side has the same shape: **reserve the outcome most visitors get rather than nothing** — `FavoritesSection` rendered `null` until it could read the cookie and then a 232 px band arrived out of nowhere on the homepage, all five blog routes and every glossary term, so the pre-mount branch now holds the empty state's box with its two lines `invisible`. And **two states that never coexist still need one height**: the coaster player's 57 px transport bar hung on `ready && !failed`, so it appeared when three.js booted on all 42 term pages that have one. Two gaps are left on purpose: the school-holiday warning (data-dependent, on 6 of 27 sampled parks) and `NearbyParksSection`, because **48 % of the 212 parks render no nearby section at all**, so a fixed reservation would collapse ~500 px on half the catalog — the same reason the glossary rides section got no padded fallback, since 115 of 267 terms have no rides. **The geometry may not depend on data, the content may:** the header's "Auslastung heute" metric only rendered once it had a value, and every input that could decide that lands after the first paint (`crowdToday.level` from the page's deliberately last query, `isOpenish` from `liveStatus ?? scheduledStatus ?? status`), so the band moved 340 → 419 px at 2059 ms on a park that gets a rating and 63 → 142 → 63 px on one that does not. It is unconditional now, like `crowdNow` beside it, with a badge, a loading pill or an em dash inside the same reserved box. A placeholder's height is **measured off the real thing, per breakpoint** — `ParkCard` hides its photo row below `sm` and is 146 px there against 366, so one 360 px placeholder over-reserved a phone by 2.4× and the featured grid collapsed 1284 px — and it has to match the real thing's **tags** too, because the diff pairs children by tag once their classes differ. **Proving a fix needs `pnpm measure:cls --late`**, not CPU throttling: the same page under the same 4× throttle measured 0.000 and 0.088 in two consecutive runs, while `--late` (shell now, streamed tail 1.5 s later, nothing throttled) reproduces Cloudflare's 0.538 for the glossary page to within 0.005, every run. The harness also sends a real `x-forwarded-for` now: from 127.0.0.1 `/api/nearby` geolocates nothing and every run settled on the nearby card's short empty state, which is how its placeholder got tuned backwards by 683 px. **And it is measured against `pnpm build && pnpm start`, at `localhost`** — both halves, because a run against `next dev` or against `127.0.0.1` reports a confident 0.0000 and looks exactly like a page with nothing wrong. `next dev` injects the stylesheet through JavaScript, so the JS-off pass (this script's whole model of the first paint) renders **unstyled** markup and every row it prints is Tailwind that had not arrived — one park page came out 8695 px "first" against 4408 px settled. And `next dev` answers **403** for `/_next/static/chunks/*` when the origin is `127.0.0.1`, which was the script's own default base: every chunk fails, the page never hydrates, and three consecutive runs graded a park page with no client JavaScript in it at all. Both are now refused rather than graded — `assertMeasurable` aborts on a failed `/_next/` subresource and on a JS-off body still sitting in the browser's serif default — and the default base is `localhost`. Two more things the dev server cannot show you: it flushes the whole document in one go, so every Suspense boundary resolves before the first paint, and its API responses are not the ones a phone waits on. See [system-overview](docs/architecture/system-overview.md#5-a-streamed-section-owes-the-page-its-height-requirement).

## API budget per page (REQUIREMENT)

the live poll sends a **projection, not the park**. `useLiveParkData` re-fetches every 5 min for as long as a tab is open, so `/api/parks/<geo>/<park>` answers with `LiveParkSnapshot` (volatile fields + each ride's id/name/slug/land) and `mergeLiveParkSnapshot` lays it back over the server-rendered park in the hook's `select` — consumers still read a complete `ParkWithAttractions`. Before adding a field anywhere in this path, decide which of four it is: **rendered + volatile** → the projection; **rendered + day-stable** → the server render, the merge carries it; **not rendered** → leave it out (`comparison` and `baseline` arrive on every attraction and have never been rendered); and **rendered + day-_scoped_**, the one that looks like the second and is not. `shows` and `restaurants` cannot move between two polls, so they were left out of both — and the server render's copy comes from a fetch cached for a day, so whatever hour that entry was written at spoke for the whole day. Written overnight, which is the usual case, it is wrong twice: the API dates showtimes to **today** and reports every show as CLOSED for as long as the **park** is, so a 04:00 entry says „yesterday's times, nothing running“ — which is what the whole site served on 2026-09-01, Phantasialand's four shows under „Keine Vorstellungen heute“ and 0 of 46 restaurants open at 13:38 against an API answering `OPERATING` for all of them. „Kurz vor der Öffnung nachladen“ does not fix it: 70 minutes before Magic Kingdom opens, the showtimes are already right and all 15 shows still read CLOSED. So the block travels on request — `?full=1` → `leanParkForLivePoll(park, { daily: true })`, asked for on a tab's first poll, every 30 min after, and once more when the park's status flips — which costs **nothing upstream**, the proxy fetches the whole park on every poll either way. Shows go whole (the API drops a show with no showtimes today, so the set is itself a statement about today), restaurants projected to their volatile fields; an absent block means unchanged, never empty. The server render is fixed from the other side: a **per-park cache tag** (`parkCacheTag` — the geo path, because `disneyland-park` is Anaheim _and_ Paris) that the backend POSTs to `/api/revalidate` with `"expire": 0` at each status flip, one small request per park per transition against a cron sweeping 213 parks on a clock that fits none of their timezones. Same rule for the card overlay — `/api/parks/live?regions=…` returns nine fields per park, never the region's park objects. And **do not merge requests just because there are several**: `stats` is a cold-compute aggregate and `best-days` a materialized snapshot, so joining them puts the fast one behind the slow one; `nowcast` timing out inside the park fetch is what used to fail the whole route's prerender. Measure with `node scripts/measure-api-calls.mjs` (needs a running site) before and after. Numbers, per-payload breakdown and the rejected consolidations: [API budget per page](docs/architecture/api-budget.md).

## The page render is the bigger half of the API budget, and it was never audited (ANTI-PATTERN)

the projection rule above was written for the five-minute poll and applied only there. The other copy of the same data — the one React serializes into `self.__next_f.push(…)` so the client can hydrate — is paid by **every request including the crawler's**, is never re-fetched, and had never been measured. It is roughly half the bytes of these pages: 199 KB of a park calendar's 444 KB, 205 KB of a park page's 500 KB. Three holes, all found by weighing the payload rather than reading the code. **A page that renders none of a thing must not ship it**: the wait-time calendar draws no attraction cards, and the only readers of `park.attractions` on that route are `ParkTodayPanel`'s headliner rows and `useParkTileItems`'s land count — between them **twelve fields, against the twenty-two it was shipping**, so `bestVisitTimes` (9.74 KB), `statistics` (5.07 KB) and `ropeDrop` (4.52 KB) rode along for forty rides nobody drew. `leanParkForCalendarShell` is an **allow**-list, not a `delete` chain like its siblings, because the kept set is the short one and a field the API adds next month then stays out by default: the list goes 39.3 → 15.2 KB, the page **−28.6 KB of HTML and −1.52 KB brotli (−2.9 %)**. **Judge it compressed and A/B it in one build**: the raw figure flatters this by 19×, brotli eats repeated JSON keys for breakfast, and the first estimate — taken by diffing a local render against a production one — read −3.2 KB because the two deploys differed for reasons that had nothing to do with the change. Rebuild both sides through the same pipeline, or the re-chunking is what you measured. **A rule written down is not a rule applied**: `comparison` and `baseline` are named in the block above as never rendered, `leanParkForLivePoll` duly omits them, and `leanParkForShell` — the server half — shipped them on every attraction of every park page for as long as both have existed (`ComparisonBadge` is real, and is wired to nothing outside `/ui`, where it is fed string literals). **And a translation namespace is as coarse as its widest consumer**: `parks` is 15.1 KB and arrives whole because 23 client components ask for `useTranslations('parks')`, so a ride page pays 3.18 KB of `parks.calendarPage` for a page with no calendar, plus `calendarView`, `bestDays`, `dayDetail` and `seasons`. Narrowing those 23 call sites to the sub-namespaces the routed map already supports (`parks.crowdLevels` and `parks.status` prove the mechanism) is worth **−3.0 KB brotli, −5.7 %** on the highest-invocation route in the app — twice the calendar trim, and the largest single item left; it is not done, because next-intl answers a missing namespace by logging MISSING_MESSAGE and rendering the raw key, so it is 23 chances to ship a visible one and wants `pnpm check:client-messages` green at each step. Restaurants are the other unclaimed 6.6 KB, held up by a component contract rather than by bytes: `useParkTileItems` reads forty-six full records for a `.length` and an `OPERATING` count, and inventing a `ParkRestaurant` with an empty `name` to satisfy the type puts a lie one render from a reader. **What makes all three expensive is which routes they land on, and it is not the popular ones.** Twelve hours of production: the park page took 1.7 K invocations, 3 min CPU, 101 MB — the **calendar** took 9.9 K / 26 min / 567 MB and the **ride page** 11 K / 22 min / 491 MB. Both are `force-dynamic`, so every origin miss is a render, and they are the two highest-cardinality routes in the site (212 parks × 22 months × 6 locales = 27,984 calendar URLs, 42,756 attraction URLs). A crawler walking a sitemap misses the CDN once per URL per TTL — each calendar URL is fetched about **0.7 times a day** and each ride URL about **0.5**, which is a daily sweep and not a cache that could ever be warm — so **cost follows the URL count, not the visitor count**, and the audit has to start from the invocation table rather than from what feels busy. It also bounds what trimming can win: a page-weight cut moves transfer and a little CPU, while the 71,000-URL crawl surface is what sets the number of renders, and only a product decision about the twenty-two-month calendar span moves that. **Measure it, do not reason about it**, and measure it on a **cache-busted** URL: `curl -H 'Accept-Encoding: identity' 'https://park.fan/…?cb=$RANDOM'`, join the `self.__next_f.push([1,"…"])` string literals, then size each field and brotli-diff the before and after. A plain fetch returns whatever Cloudflare is holding — a `cf-cache-status: HIT` copy of the park page showed `statistics` and `bestVisitTimes` absent from its attractions and a fresh render of the same URL had both, which reads exactly like a projection that is already working. See [API budget → the other copy](docs/architecture/api-budget.md#the-other-copy-what-the-server-render-serializes).

## A `revalidate` at a call site is somebody else's page (REQUIREMENT)

Next takes the **shortest** `revalidate` among the fetches a route executes, and `export const revalidate` does not override it — it is a default any shorter fetch beats, which was verified by declaring a week on the blog route and watching the manifest not move a single page. So a number typed into a component decides how often a whole class of pages rebuilds, and every rebuild is an ISR write **and** a full SSR render. `lib/blog/park-resolver.ts` asked for `getGeoStructure(3600)` to index park slugs for `ref:` links and thereby held **all 60 blog posts** to 24 rebuilds a day; `hero-stats` and `hero-world-panel` did the same to the homepage with `getGlobalStats(3600)` / `getGeoLiveStats(3600)`. `lib/api/ml.ts` had it written down backwards — „cached 1h — anything lower would pin the homepage shell's ISR window below its 3600s", as if the hour protected the homepage, when `MLStatsSection` reaches it through the AI story chapter and that fetch **was** the window, for a figure that changes once a day at 06:00 UTC. So: **never pass a numeric TTL at a call site**, put it in `CACHE_TTL` or the helper's default, and **set it from the data's cadence rather than as a floor under some page**. A seed with a client overlay may cache for a long time — `getGlobalStats`/`getGeoLiveStats` say „Only an SSR SEED" in their own docstrings and are replaced on mount — but where there is **no** overlay and the value is compared against a threshold, stale is _wrong_ rather than old, which is why the hottest-parks heat banner was removed instead of slowed down. A parameter is still right when the window belongs to the caller (`getParkWeatherNowcast` is load-bearing on one page and decoration in a blog post), provided the constant is named and the docstring says why. Finding these by grepping components missed the homepage four times; what works is walking the route's **import graph** for every reachable `revalidate` literal, then proving it against `initialRevalidateSeconds` in `.next/prerender-manifest.json` before and after a build. Measured: **5,032 → 657 regenerations/day, −86.9 %**. See [caching strategy](docs/architecture/caching-strategy.md#the-invisible-clock-a-hard-coded-ttl-argument-sep-2026).

## Translations are routed, not bundled (REQUIREMENT)

everything handed to `NextIntlClientProvider` is serialized into the RSC payload — and the HTML — of every page that renders it, ×6 locales. So the locale layout ships **only the chrome** (`LAYOUT_MESSAGE_NAMESPACES`, ~6 KB) and each route adds its delta via `<RouteMessages route="…">` in its `page.tsx`. Both lists are **derived from the import graph** by `pnpm generate:route-namespaces` into the committed `i18n/route-namespaces.generated.ts` — never hand-edit it; after moving a component across the client boundary, re-run the generator. The merge happens **client-side** (`useMessages()` + `mergeMessages`) because a nested next-intl provider _replaces_ messages instead of merging them, so shipping the union would serialize the chrome set twice per page. A namespace that a route needs but doesn't ship does not throw: next-intl logs MISSING_MESSAGE and renders the raw key, which is why `pnpm check:client-messages` fails on a stale map, a missing wrapper, a wrong route key and a superfluous wrapper alike. Judge changes on the **compressed** number — the old flat allowlist looked like it saved 10 KB of JSON and was worth 2.3 KB after brotli. Namespaces only a cookie-gated section needs (`parks`+`attractions` for `FavoritesSection`) are declared in `LAZY_MESSAGE_BOUNDARIES` and **fetched** as a per-locale chunk instead, which requires the eager skeleton to keep reserving the same box so the swap costs no CLS. See [internationalization](docs/i18n/internationalization.md#which-namespaces-reach-the-client).
