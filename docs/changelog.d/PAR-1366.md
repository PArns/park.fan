### Ein Entwicklerportal unter `/developers`: API-Doku, Berechtigungen pro Key und Key-Anträge, die im Admin zum Key werden

Einen Daten-Key gab es bisher nur per Mail an hello@park.fan. Was offen ist und was einen Key
braucht, stand verteilt in Impressum, `auth.md` und Swagger. `/[locale]/developers` (Tool-Seite,
alle sechs Sprachen, `app/[locale]/developers/page.tsx`) bringt es auf eine Seite: offene Routen
mit den Limits ohne Key (60 pro Minute, 1.000 pro Stunde), fünf Berechtigungen mit ihren Routen,
Key mitschicken und prüfen (`/v1/api-keys/verify`), die fünf Fehlercodes mit Status, das
Stundenlimit, der Hinweis, dass der Key auf den eigenen Server gehört, Referenz, MCP, Bedingungen
und FAQ.

Die Berechtigungen kommen aus einem Katalog, `lib/developers/scopes.ts`: `forecasts`, `planner`,
`statistics`, `curated`, `travel`. Portal, Antragsformular und Admin lesen alle dieselbe Liste.
Prognosen und Planer setzt die API schon durch, die anderen drei zeigt die Seite als „Key bald
Pflicht“. Speichern und Durchsetzen ist Sache der API (PAR-1365). Bis dahin öffnet jeder Key
Prognosen und Planer (`LEGACY_KEY_SCOPES`). Das Admin schickt `scopes` erst mit, wenn die Key-Liste
der API das Feld trägt (`apiStoresScopes`).

Das Antragsformular (`components/developers/key-request-form.tsx`) fragt Name, E-Mail, Firma,
Projektname, Website, Art, Beschreibung (ab 40 Zeichen), Open Source mit Repository, Finanzierung,
Berechtigungen, Anfragen pro Tag, Parks und Nachricht ab, mit Turnstile (`developer-key-request`).
Bei der Finanzierung sind mehrere Antworten möglich, „gar nicht“ steht allein. Werbung,
Affiliate- oder bezahlte Links, ein Preis oder Abo, Auftragsarbeit und ein Firmenprodukt gelten
als kommerziell. Das Formular zeigt dann vor dem Absenden den Hinweis auf die Vereinbarung.
`POST /api/developers/key-request` prüft mit demselben Schema (`lib/developers/key-request.ts`) und
legt jeden Antrag als privates JSON unter `developer-requests/<id>.json` im Blob-Store ab. Ein
zweiter offener Antrag derselben Adresse bekommt 409, ab 300 offenen Anträgen gibt es 503.
Lesen und Schreiben von privatem JSON liegt jetzt in `lib/storage/private-json.ts`. Die
Content-Change-Daten und die Einsendungen nutzen es auch, der Treiber ist nach
`lib/storage/driver.ts` umgezogen.

Auf `/admin/api-keys` stehen über den Keys die Anträge. „Key erstellen“ füllt den Dialog aus dem
Antrag (`keyRequestPrefill`): Projektname, Adresse, kommerziell oder nicht, Stundenlimit aus dem
Volumen (mindestens 1.000, ohne eigenes Limit bei mehr als 100.000 pro Tag), Berechtigungen und eine
Notiz. Danach ist der Antrag bewilligt, und „Antwort mit Key“ öffnet eine Mail mit Key, `curl`-Zeile,
Limit und Links, auf Deutsch für die deutsche Seite, sonst auf Englisch. „Ablehnen“ nimmt einen
Grund, der in der Absage-Mail steht. Ein abgelehnter Antrag lässt sich wieder öffnen, und Löschen
entfernt den Antrag, aber nie den Key. `pnpm test:developer-key-requests` prüft Schema,
Finanzierung, Vorbelegung, Scopes und Mails (19 Fälle).

Die 308 von `/developers` auf `api.park.fan/api` ist entfernt. Footer („API Dokumentation“),
Sitemap, Impressum (Abschnitt „Prognosen und eigene Daten nur mit API-Key“), `auth.md`, `llms.txt`,
der Skill `park-fan-data`, die Beschreibung von `get_park_best_days` und `server.json` verweisen
jetzt auf das Portal. Mehr dazu in der [Feature-Doku](../features/developer-portal.md).
