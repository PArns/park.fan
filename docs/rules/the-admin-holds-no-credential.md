# The admin holds no credential (REQUIREMENT)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

`/admin` authenticates with an **httpOnly session cookie** — client code sends nothing, `adminFetch` is a plain same-origin fetch, and `app/api/admin/[...path]` turns the cookie into `Authorization: Bearer …` server-side. The shared password in `sessionStorage` it replaced was readable by any script on the origin and unlocked every administrative endpoint on api.park.fan, which until this change had **no guard of its own at all** — the `?pass=` it advertised was checked by a Cloudflare rule and by nothing in the application. Four things in the proxy are load-bearing and were each a bug before: it must export **every verb** (the editing API uses PATCH and DELETE, which 405'd at Next), it must not call `response.json()` unconditionally (a 204 from a logout or a delete threw), it must move a re-issued token from a password change into the cookie — passing it through would leave the browser holding a cookie that was just revoked, i.e. logged out by succeeding — and it must **validate** that cookie against `auth/me` rather than notice one is set, because reading a cookie back only proves the caller can send a header: `Cookie: parkfan_admin_session=x` satisfied the gate written to keep strangers away from `getServerApiHeaders()`'s `x-auth-key`, the header the API reads as "this is our own frontend" and therefore as licence to skip the throttler and to trust the forwarded address. Not `requireAdmin` though: the password change and the TOTP enrolment are behind this proxy and a session owing either must still reach them, so the role floor stays where the API enforces it. The deprecated `pass` query parameter is dropped rather than relayed. The login form carries the **same Turnstile challenge `/contribute` uses** (widget now `components/common/turnstile-widget.tsx`, verify `lib/security/turnstile.ts`), checked in `/api/admin/session` **before** the credentials are forwarded — everything behind it only counts attempts that were already made, and the per-account lockout is a weapon pointed the wrong way, since anybody who knows an editor's address can spend their five tries and keep them out. A token is **single-use**, so a two-factor login solves twice and the form resets its widget in the `finally` of every attempt; a missing secret in production is a hard failure, so an unset `TURNSTILE_SECRET_KEY` locks the admin out rather than leaving it open. **`success: true` is not the answer to „may this proceed"**: Cloudflare confirms a token is genuine and says nothing about which form it was solved on, so the **action** (`TURNSTILE_ACTIONS`, its own `server-only`-free file so widget and check share it across the client boundary) and the **hostname** (`TURNSTILE_HOSTNAMES`) are checked too — `/contribute` shares this widget and is a challenge anybody may solve as often as they like, so without the action check the upload form is a token vending machine for the admin login. The two unconfigured cases are asymmetric on purpose: a missing secret refuses in production, a missing hostname allowlist **skips** its check, because an unset variable must not be able to take both forms down on the deploy that shipped it (`pnpm test:turnstile`). **This side is not the only side:** `/v1/admin/auth/login` is public, so a bot skipping this app never meets the challenge — the API asks for a solved token from every caller that does _not_ send a valid `THROTTLE_BYPASS_KEYS` value, and this app is exempt because it already redeemed the token (single-use), which is also why the API cannot be the only verifier without a lockstep deploy. The second-factor step **looks like six boxes and is one input** — the boxes are drawn and a transparent field lies over the row. The six real inputs it replaced could not be autofilled and it was one line: `value.replace(/\D/g,'').slice(-1)` per box is right for a person typing one digit and wrong for 1Password, which writes all six characters into the first box in a single event — the slice kept the last of them, so a fill produced a lone `6` and five empty boxes, with no error anywhere. `autocomplete="one-time-code"` belongs on one field, **and it is the only fillable field on that step**: a `readOnly` username rode along hidden there until a real 1Password test came back negative twice, through the form key and through the sibling forms, which rules out DOM identity as the cause and leaves the field itself as the likeliest one — an `autocomplete="username"` input beside any other fillable field is what a login-form detector keys on, hidden or not. It is gone, and whether that moves 1Password is a person's test too. A complete code submits itself, because six pasted digits behind a button save nobody the typing. The step change **replaces the `<form>` element** rather than swapping its children, and `pnpm check:admin-login-step` is what holds that: it drives the step change in a browser with `/api/admin/session` stubbed (401 to the gate's probe, `totp-required` to the form's POST) and `window.turnstile` defined before the app loads, and it fails when both steps share one node. Whether a password manager then re-reads that form is a person's test and stays one. The back button stays live while an attempt is in flight, so an answer can arrive for a step nobody is standing on: what it says about the **step** — the move to the code step, the error message, the field resets — is applied only while the operator is still on the step the request was sent from and lapses silently otherwise, and what it says about the **account or the session** — `ok`, `locked`, `rate-limited` — is applied whichever form is showing, because a lockout is true on both and a login screen drawn over a live session is worse than an unexpected dashboard. `needsTotpRef` is what tells the two apart, and it is written where the step changes rather than left to the effect that syncs it after a render, because the answer can land before that effect flushes. The curated-field editor is **generated from backend descriptors**, so a new curated column appears with no frontend change; two of its controls exist for a reason — a curated height of `0` means "no minimum at all" and empty means "accept upstream", and a curated boolean has three states because a curated `false` is a real correction. Media and blog stay a separate write model (files → pull request), which is why the entity media panel is a view with links rather than an editor. See [admin](docs/features/admin.md).
