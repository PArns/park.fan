# park.fan Frontend

Theme park wait times and statistics frontend for **[api.park.fan](https://api.park.fan)**.
**Technology Stack:** Next.js 16 (App Router), React 19, TypeScript.
**Routing:** This project uses **`proxy.ts`** for routing and i18n middleware, **not** a standard `middleware.ts`.
Multilingual (EN/DE/NL/FR/ES/IT), Server Components by default. All detailed documentation lives in **`docs/`** - start at **[docs/README.md](docs/README.md)**.
**Park page loading priority (REQUIREMENT):** the best-travel-time data (best-days calendar + historical stats) must **always load last** — live status, wait times and all weather queries load first. Enforced via `useLoadLast` (`lib/hooks/use-load-last.ts`); see [system-overview](docs/architecture/system-overview.md#4-park-page-loading-priority-requirement).
**API budget per page (REQUIREMENT):** the live poll sends a **projection, not the park**. `useLiveParkData` re-fetches every 5 min for as long as a tab is open, so `/api/parks/<geo>/<park>` answers with `LiveParkSnapshot` (volatile fields + each ride's id/name/slug/land) and `mergeLiveParkSnapshot` lays it back over the server-rendered park in the hook's `select` — consumers still read a complete `ParkWithAttractions`. Before adding a field anywhere in this path, decide which of three it is: **rendered + volatile** → the projection; **rendered + day-stable** → the server render, the merge carries it; **not rendered** → leave it out (`comparison` and `baseline` arrive on every attraction and have never been rendered). Same rule for the card overlay — `/api/parks/live?regions=…` returns nine fields per park, never the region's park objects. And **do not merge requests just because there are several**: `stats` is a cold-compute aggregate and `best-days` a materialized snapshot, so joining them puts the fast one behind the slow one; `nowcast` timing out inside the park fetch is what used to fail the whole route's prerender. Measure with `node scripts/measure-api-calls.mjs` (needs a running site) before and after. Numbers, per-payload breakdown and the rejected consolidations: [API budget per page](docs/architecture/api-budget.md).
**Translations are routed, not bundled (REQUIREMENT):** everything handed to `NextIntlClientProvider` is serialized into the RSC payload — and the HTML — of every page that renders it, ×6 locales. So the locale layout ships **only the chrome** (`LAYOUT_MESSAGE_NAMESPACES`, ~6 KB) and each route adds its delta via `<RouteMessages route="…">` in its `page.tsx`. Both lists are **derived from the import graph** by `pnpm generate:route-namespaces` into the committed `i18n/route-namespaces.generated.ts` — never hand-edit it; after moving a component across the client boundary, re-run the generator. The merge happens **client-side** (`useMessages()` + `mergeMessages`) because a nested next-intl provider _replaces_ messages instead of merging them, so shipping the union would serialize the chrome set twice per page. A namespace that a route needs but doesn't ship does not throw: next-intl logs MISSING_MESSAGE and renders the raw key, which is why `pnpm check:client-messages` fails on a stale map, a missing wrapper, a wrong route key and a superfluous wrapper alike. Judge changes on the **compressed** number — the old flat allowlist looked like it saved 10 KB of JSON and was worth 2.3 KB after brotli. Namespaces only a cookie-gated section needs (`parks`+`attractions` for `FavoritesSection`) are declared in `LAZY_MESSAGE_BOUNDARIES` and **fetched** as a per-locale chunk instead, which requires the eager skeleton to keep reserving the same box so the swap costs no CLS. See [internationalization](docs/i18n/internationalization.md#which-namespaces-reach-the-client).
**Reuse existing components (REQUIREMENT):** always reuse existing components (e.g. `ParkStatusBadge`, `CrowdLevelBadge`, `Badge`, `ParkCard`) instead of re-implementing UI inline — keeps styling/colors consistent. Only build new when nothing suitable exists. See [conventions](docs/development/conventions.md#11-reuse-existing-components).
**three.js animations (REQUIREMENT):** research the real-world reference **first**, then implement; and **verify every animation from all camera perspectives** (coaster player: Front, Follow, Onboard) across the whole timeline and both day/night themes via the headless render harness (`node scripts/render-coaster-elements.mjs`) before shipping — a green build is not enough. See [conventions](docs/development/conventions.md#12-threejs-animations-research-first-then-verify-from-every-perspective-requirement).
**Ride ↔ Glossary link:** rides carry a curated `rideProfile` from the API (track figures **in ride order**, ride type, builder) stored as **glossary term ids**, so the ride page links into the glossary (`RideProfileSection`) and each term page lists the rides that feature it (`GlossaryTermRides`). Element order is meaningful and repeats are intentional — never dedupe or sort it. Adding/renaming a term means regenerating the API's allowlist via `node scripts/export-glossary-term-ids.mjs`. See [glossary](docs/features/glossary.md#ride--glossary-link).
**Umami event budget (REQUIREMENT):** Umami Cloud bills **every event property as another event**, so a 5-property event costs 6× a pageview and the plan (100k/month) is blown by properties, not traffic. Before adding one: never send what Umami already has (URL, referrer, `navigator.language` → so no `locale`, no `path`) and never send what a sibling property implies (`in_park` was `type === 'in_park'`, `hasQuery` was `queryLength > 0`). Events firing on **load** cost their property count on every pageview — price them accordingly. Keep `data-exclude-hash="true"` on the script tag: the tracker patches `replaceState` and bills a changed hash as a fresh pageview, which the park tabs and the calendar month stepper both write. See [analytics](docs/development/analytics.md).
**No text may read as AI-generated (REQUIREMENT):** this covers **every** string a human ever sees, not just blog posts — image `alt` and `caption` in the media sidecars, UI copy, PR bodies, commit messages, docs. The tells to avoid are structural, not just lexical: the same sentence skeleton repeated across a set (subject + participle clause + "behind it / in front of it"), an exhaustive inventory of everything in frame, mood adjectives nobody asked for (`bathed in`, `against a summer sky`, `sweeping the night sky`), and a caption that restates the alt text. Write what a person would write: **alt** is short and factual, for somebody who cannot see the picture; **caption** is what you would say pointing at it, and is allowed to be a fact, a joke or nothing. Vary the shape between neighbouring entries — six captions in a row starting with the ride name is itself the tell. Details and the do/don't table for prose: [blog authoring guide](content/blog/README.md#8-writing-style-requirement); for image text: [public/media/README.md](public/media/README.md).
**Blog writing style (REQUIREMENT):** posts must not read as AI-generated. **Never use „ehrlich" in any form** (`ehrlich gesagt`, `der ehrlichste …`, `um ehrlich zu sein`) — it is the clearest tell — and avoid the register around it: no `bezahlte Vorfahrt`, `Datenpunkt`, `die These dieses Artikels`, `X-Währung`, `Fairness-Hinweis in eigener Sache`, no announcing the article's own structure, no unsourced superlatives, and **no em dash `—` in running text** (wrong character in German anyway — use `–`, a comma or a full stop; the only `—` in a post is the `— Patrick` signature). German grammar counts too — check the article before "correcting" one in (it is **das** Efteling, like `das Toverland` and `das Phantasialand` → `bis zum Efteling`, `im Vergleich zum Efteling`, but `das Efteling ist …` — never `der`/`die`). Full do/don't table + voice reference in the [blog authoring guide](content/blog/README.md#8-writing-style-requirement).
**Park/Ride page ↔ blog link:** park pages list the posts about that park, ride pages the posts about that ride (`ParkBlogPostsSection` / `AttractionBlogPostsSection`, reverse index in `lib/blog/backlinks.ts`). The relation is derived from the post itself (`ref:`/widget references, a ride counts for its park too, plus `relatedParks`/`relatedAttractions`), so a round-up like the Halloween guide lands on all ten park pages without a list. `parkLinks` / `rideLinks` in the frontmatter override it (`false` = never, or an explicit list; `rideLinks` also takes `parkSlug/*`), are **independent of each other** and are resolved **per post, not per locale** — setting one in any language governs all six, and `pnpm generate:blog-manifest` warns when translations disagree or an entry isn't a valid slug. See the [blog authoring guide](content/blog/README.md#the-other-direction-park-and-ride-pages-linking-back).
**Media database (REQUIREMENT):** every image — park, ride, blog, diagram — lives in ONE filesystem-backed database at `public/media/<collection>/`, with a `<name>.json` sidecar per image. **A collection is storage, the sidecar is the index:** nothing queries by folder, so a Halloween photo of Troy sits in `toverland-halloween` and still answers `getRideImages('toverland','troy')`. Never infer park/ride/role from a filename or folder. Read from `@/lib/media` (structure + search), `@/lib/media/text` (localized alt/caption — 37 KB, import only where text is rendered) and `@/lib/media/hero` (**the only client-safe one** — importing `@/lib/media` into a Client Component ships the 107 KB catalog). Image URLs carry `?v=<content hash>` because retargeting a focal point rewrites a crop's bytes at an unchanged URL; `images.localPatterns` in `next.config.ts` is what permits that query. `focus` is one point per image driving BOTH the CSS `object-position` on every card/background AND the offset the build-time 16:9/4:3/1:1 crops are cut at. Authoring contract: [public/media/README.md](public/media/README.md); full docs: [media database](docs/features/media-database.md).
**Card photos are two layers (REQUIREMENT):** `object-fit: cover` scales to the **larger** of the two ratios it needs, so it overflows on one axis and fits exactly on the other — paint a photo across a whole card (405×404, aspect ≈1.0) and a 4:3 photo fills its _height_ exactly, leaving `object-position`'s Y with nothing to move. The focal point then renders byte-identical pixels however far you drag it, with a green build and no error. So the framing reference is the **strip between the glass panels**, not the card: `CardPhotoFrame` lives inside the card's photo-spacer row (405×220, aspect 1.84) and is what a visitor sees; `CardPhoto` still covers the whole card underneath so the frosted panels have something to blur. Same URL → one request, one decode. Where a card renders no bottom panel (ride with no live wait time) the spacer takes `row-span-2`, or the framed layer's lower edge sits exposed mid-card as a crop seam. Never widen the frame layer back to the full card. `pnpm check:card-framing` (needs a running site) asserts the box stays wider than 1.5. See [media database](docs/features/media-database.md).
**Blog manifest is split (REQUIREMENT):** the generator writes `manifest.ts` (frontmatter + build-time derivations, small) and `manifest-bodies.ts` (~900 KB of markdown). Galleries are no longer its job — they come from the media database. Import listings from **`@/lib/blog/listing`** — `@/lib/blog` drags every post body into that route's bundle, and it is imported by the root layout, the homepage and every park page. Body-derived values (reading time, `parkRefs`) are computed at build time by the shared `lib/blog/derive.mjs`, never a second copy of those regexes. See [scripts](docs/development/scripts.md#the-blog-manifest-is-three-files-on-purpose).
**Blog spotlight cards:** `ParkCard`/`AttractionCard` lay out via `row-span-3` + `grid-template-rows: subgrid`, so the row template must sit **on the card itself**, never on a shared wrapper that also holds the heading — `auto` tracks collapse against the panels' `-mb-4`/`-mt-4` and slice the title and wait time. Use `grid [grid-template-rows:auto_2rem_auto] sm:[grid-template-rows:auto_minmax(220px,1fr)_auto]`; the `2rem` absorbs that overlap once the photo is hidden below `sm`, and `minmax(220px,1fr)` keeps image-less cards full height.
**Localized blog gallery captions:** a gallery is a **collection** in the media database, and its captions live per image in the sidecar (`alt`/`caption` as `{de,en,nl,fr,es,it}`) — the old `captions.json` + five `captions.<locale>.json` files per folder are gone. A post may still override a caption inline; the same photo legitimately reads differently in two articles. See [public/media/README.md](public/media/README.md).
