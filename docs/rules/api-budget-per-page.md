# API budget per page (REQUIREMENT)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

the live poll sends a **projection, not the park**. `useLiveParkData` re-fetches every 5 min for as long as a tab is open, so `/api/parks/<geo>/<park>` answers with `LiveParkSnapshot` (volatile fields + each ride's id/name/slug/land) and `mergeLiveParkSnapshot` lays it back over the server-rendered park in the hook's `select` — consumers still read a complete `ParkWithAttractions`. Before adding a field anywhere in this path, decide which of four it is: **rendered + volatile** → the projection; **rendered + day-stable** → the server render, the merge carries it; **not rendered** → leave it out (`comparison` and `baseline` arrive on every attraction and have never been rendered); and **rendered + day-_scoped_**, the one that looks like the second and is not. `shows` and `restaurants` cannot move between two polls, so they were left out of both — and the server render's copy comes from a fetch cached for a day, so whatever hour that entry was written at spoke for the whole day. Written overnight, which is the usual case, it is wrong twice: the API dates showtimes to **today** and reports every show as CLOSED for as long as the **park** is, so a 04:00 entry says „yesterday's times, nothing running“ — which is what the whole site served on 2026-09-01, Phantasialand's four shows under „Keine Vorstellungen heute“ and 0 of 46 restaurants open at 13:38 against an API answering `OPERATING` for all of them. „Kurz vor der Öffnung nachladen“ does not fix it: 70 minutes before Magic Kingdom opens, the showtimes are already right and all 15 shows still read CLOSED. So the block travels on request — `?full=1` → `leanParkForLivePoll(park, { daily: true })`, asked for on a tab's first poll, every 30 min after, and once more when the park's status flips — which costs **nothing upstream**, the proxy fetches the whole park on every poll either way. Shows go whole (the API drops a show with no showtimes today, so the set is itself a statement about today), restaurants projected to their volatile fields; an absent block means unchanged, never empty. The server render is fixed from the other side: a **per-park cache tag** (`parkCacheTag` — the geo path, because `disneyland-park` is Anaheim _and_ Paris) that the backend POSTs to `/api/revalidate` with `"expire": 0` at each status flip, one small request per park per transition against a cron sweeping 213 parks on a clock that fits none of their timezones. Same rule for the card overlay — `/api/parks/live?regions=…` returns nine fields per park, never the region's park objects. And **do not merge requests just because there are several**: `stats` is a cold-compute aggregate and `best-days` a materialized snapshot, so joining them puts the fast one behind the slow one; `nowcast` timing out inside the park fetch is what used to fail the whole route's prerender. Measure with `node scripts/measure-api-calls.mjs` (needs a running site) before and after. Numbers, per-payload breakdown and the rejected consolidations: [API budget per page](docs/architecture/api-budget.md).
