# A `<lastmod>` is observed, never stamped (REQUIREMENT)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

Google ignores `changefreq` and `priority` outright, so until the content-change crawl existed the attraction sitemaps carried **42,756 URLs and no signal at all**, and the main one dated 1,662 of 3,480 — the glossary and the blog, the two things that are files in this repo with a date on them. The API has no per-entity content timestamp (`/v1/sitemap/attractions` answers `{url, slug}`; a park payload dates only its live readings), so the date is **observed**: a daily 05:30 UTC run fingerprints the _stable_ half of every park and ride, and the day the fingerprint moves is the day the page changed (`lib/seo/content-changes/`, snapshot in Vercel Blob because it has to outlive both a deploy and an ISR regeneration). **The whole value is in what stays out of the hash.** A park page repaints every five minutes, so `queues`, `status`, `crowdLevel`, `statistics`, `typicalWaits`, `bestVisitTimes`, `ropeDrop`, `isHeadliner`, `isCurrentlyInSeason`, `weather`, `schedule` and `analytics` are excluded by hand — let one of them in and all 44,000 URLs change every morning, which is a build stamp, and one identical value everywhere is exactly what gets a sitemap's lastmod discounted, taking the glossary's and the blog's honest dates down with it. In goes what a reader sees and what stays put: name, land, height limits, the ride profile with its glossary terms, the curated park facts, the media versions and the blog backlinks. Three rules are load-bearing and each fixed a real hole: a park the API did not answer **keeps its dates** (`retainUncovered`), because dropping it re-adds its rides tomorrow and a re-add reads as a change — one timeout would be 82 false recrawl invitations; a **`FINGERPRINT_VERSION` bump** adopts the new hashes and keeps every date, since editing the detector is not the catalog changing; and which rides count comes from `getAttractionPaths()`, the sitemap's own list, not from re-deriving the variant-slug rule against the park payload — the two disagree on seven rides, which was seven `<lastmod>` values for URLs no sitemap lists. The same snapshot feeds IndexNow, which used to submit all ~46,000 URLs every morning and now sends the paths that moved (Mondays still sweep everything, so a detector that stops detecting cannot silently mute the route; `?dry=1` builds the list without sending it). `pnpm test:content-changes` pins the blindness and the three rules, because a green build shows none of it. See [sitemaps](docs/seo/sitemaps.md#lastmod-observed-not-stamped).
