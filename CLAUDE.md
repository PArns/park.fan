# park.fan Frontend

Theme park wait times and statistics frontend for **[api.park.fan](https://api.park.fan)**.
**Technology Stack:** Next.js 16 (App Router), React 19, TypeScript.
**Routing:** This project uses **`proxy.ts`** for routing and i18n middleware, **not** a standard `middleware.ts`.
Multilingual (EN/DE/NL/FR/ES/IT), Server Components by default. All detailed documentation lives in **`docs/`** - start at **[docs/README.md](docs/README.md)**.
**Park page loading priority (REQUIREMENT):** the best-travel-time data (best-days calendar + historical stats) must **always load last** — live status, wait times and all weather queries load first. Enforced via `useLoadLast` (`lib/hooks/use-load-last.ts`); see [system-overview](docs/architecture/system-overview.md#4-park-page-loading-priority-requirement).
**A streamed section owes the page its height (REQUIREMENT):** the park page buys TTFB by streaming its slow parts, and the bill arrives as CLS — charged to whatever the visitor is looking at when the boundary resolves. So a `<Suspense>` fallback must reserve the height its content will take. `fallback={null}` is honest only when nothing renders below it: the blog section had one and did **no async work at all** (`hasPublishedPosts`/`getPostsForPark` read the generated manifest synchronously, the lone `await getTranslations` hits messages the render already holds), so the boundary deferred nothing and dropped 467 px of content out of thin air — synchronous data belongs inline, in the first HTML, at full height. And a fallback should render whatever needs **no** data rather than a grey box shaped like it: the best-days header is data-free and its height depends on how the park name wraps (one line on desktop, two on a phone), which sized `Skeleton` blocks were 66–120 px short of until the fallback started rendering the real `ParkBestDaysHeader`. Measure the three states a visitor can observe — fallback, server seed, settled queries — and diff the block geometry; that delta _is_ the shift, and seed → settled measures 0, so the client queries were never it. And on a **prerendered** route a boundary defers nothing whatsoever: the project runs no PPR, so the prerender waits for it anyway and the resolved markup already sits in the shipped `.html`, sorted to the end of the byte stream in a `<div hidden id="S:1">` and grafted in by the `$RC()` after it — which is how the glossary term page dropped 396–1463 px into the column two seconds after paint and pushed the "back to dictionary" button (`div.pb-2`, the element Cloudflare names) down with everything under it. The client side has the same shape: **reserve the outcome most visitors get rather than nothing** — `FavoritesSection` rendered `null` until it could read the cookie and then a 232 px band arrived out of nowhere on the homepage, all five blog routes and every glossary term, so the pre-mount branch now holds the empty state's box with its two lines `invisible`. And **two states that never coexist still need one height**: the coaster player's 57 px transport bar hung on `ready && !failed`, so it appeared when three.js booted on all 42 term pages that have one. Two gaps are left on purpose: the school-holiday warning (data-dependent, on 6 of 27 sampled parks) and `NearbyParksSection`, because **48 % of the 212 parks render no nearby section at all**, so a fixed reservation would collapse ~500 px on half the catalog — the same reason the glossary rides section got no padded fallback, since 115 of 267 terms have no rides. **The geometry may not depend on data, the content may:** the header's "Auslastung heute" metric only rendered once it had a value, and every input that could decide that lands after the first paint (`crowdToday.level` from the page's deliberately last query, `isOpenish` from `liveStatus ?? scheduledStatus ?? status`), so the band moved 340 → 419 px at 2059 ms on a park that gets a rating and 63 → 142 → 63 px on one that does not. It is unconditional now, like `crowdNow` beside it, with a badge, a loading pill or an em dash inside the same reserved box. A placeholder's height is **measured off the real thing, per breakpoint** — `ParkCard` hides its photo row below `sm` and is 146 px there against 366, so one 360 px placeholder over-reserved a phone by 2.4× and the featured grid collapsed 1284 px — and it has to match the real thing's **tags** too, because the diff pairs children by tag once their classes differ. **Proving a fix needs `pnpm measure:cls --late`**, not CPU throttling: the same page under the same 4× throttle measured 0.000 and 0.088 in two consecutive runs, while `--late` (shell now, streamed tail 1.5 s later, nothing throttled) reproduces Cloudflare's 0.538 for the glossary page to within 0.005, every run. The harness also sends a real `x-forwarded-for` now: from 127.0.0.1 `/api/nearby` geolocates nothing and every run settled on the nearby card's short empty state, which is how its placeholder got tuned backwards by 683 px. See [system-overview](docs/architecture/system-overview.md#5-a-streamed-section-owes-the-page-its-height-requirement).
**API budget per page (REQUIREMENT):** the live poll sends a **projection, not the park**. `useLiveParkData` re-fetches every 5 min for as long as a tab is open, so `/api/parks/<geo>/<park>` answers with `LiveParkSnapshot` (volatile fields + each ride's id/name/slug/land) and `mergeLiveParkSnapshot` lays it back over the server-rendered park in the hook's `select` — consumers still read a complete `ParkWithAttractions`. Before adding a field anywhere in this path, decide which of three it is: **rendered + volatile** → the projection; **rendered + day-stable** → the server render, the merge carries it; **not rendered** → leave it out (`comparison` and `baseline` arrive on every attraction and have never been rendered). Same rule for the card overlay — `/api/parks/live?regions=…` returns nine fields per park, never the region's park objects. And **do not merge requests just because there are several**: `stats` is a cold-compute aggregate and `best-days` a materialized snapshot, so joining them puts the fast one behind the slow one; `nowcast` timing out inside the park fetch is what used to fail the whole route's prerender. Measure with `node scripts/measure-api-calls.mjs` (needs a running site) before and after. Numbers, per-payload breakdown and the rejected consolidations: [API budget per page](docs/architecture/api-budget.md).
**Translations are routed, not bundled (REQUIREMENT):** everything handed to `NextIntlClientProvider` is serialized into the RSC payload — and the HTML — of every page that renders it, ×6 locales. So the locale layout ships **only the chrome** (`LAYOUT_MESSAGE_NAMESPACES`, ~6 KB) and each route adds its delta via `<RouteMessages route="…">` in its `page.tsx`. Both lists are **derived from the import graph** by `pnpm generate:route-namespaces` into the committed `i18n/route-namespaces.generated.ts` — never hand-edit it; after moving a component across the client boundary, re-run the generator. The merge happens **client-side** (`useMessages()` + `mergeMessages`) because a nested next-intl provider _replaces_ messages instead of merging them, so shipping the union would serialize the chrome set twice per page. A namespace that a route needs but doesn't ship does not throw: next-intl logs MISSING_MESSAGE and renders the raw key, which is why `pnpm check:client-messages` fails on a stale map, a missing wrapper, a wrong route key and a superfluous wrapper alike. Judge changes on the **compressed** number — the old flat allowlist looked like it saved 10 KB of JSON and was worth 2.3 KB after brotli. Namespaces only a cookie-gated section needs (`parks`+`attractions` for `FavoritesSection`) are declared in `LAZY_MESSAGE_BOUNDARIES` and **fetched** as a per-locale chunk instead, which requires the eager skeleton to keep reserving the same box so the swap costs no CLS. See [internationalization](docs/i18n/internationalization.md#which-namespaces-reach-the-client).
**Parks we cannot read (REQUIREMENT):** Hansa-Park publishes wait times only in its own app on the park WLAN, so no number will ever arrive for it — and a park with no source is **indistinguishable from a park shut for the night** in the payload (at 03:00 every park has zero rides operating and empty `queues`). So never derive it: the API's curated `liveWaitTimes` (`{available, reason}`) is the only signal, read through `noLiveWaitTimesReason()` / `hasReadableWaitTimes()` in `lib/utils/live-wait-times.ts`, which treats an absent field as available so older/cached responses keep behaving as before. It is **not** a freshness check — a feed that went quiet an hour ago stays `available: true`. Left alone, the page fills the gap with the shape of a quiet park: 82 of 82 rides "running" at `very_low`, Ø 0 min, plus an ML forecast built on zero observations. Crowd badges need no special case (the API sends `unknown` → "keine Prognose"); the listing surfaces **strip** `crowdLevel`/`averageWaitTime`/`operatingAttractions` at the projection boundary rather than shipping the flag, because the poll re-downloads its nine fields per park every 5 min and this one never changes. See [parks without wait times](docs/api/parks-without-wait-times.md).
**A ride out of season is closed, and is not one of the park's rides today (REQUIREMENT):** Phantasialands Schlittschuhverleih läuft im November, Dezember und Januar — und stand am 21. August auf der Parkseite als **geöffnet** bei `very_low`, während seine eigene Seite **geschlossen** lieferte, aus derselben Datenbankzeile. Schuld war der optimistische Fallback der Ride-Liste: kommt keine Queue-Zeile an und ist der Park offen, gilt die Bahn als offen. Der ist für einen Feed gedacht, der stehengeblieben ist — über eine Eisbahn im August meldet niemand etwas, weil es nichts zu melden gibt, und aus dieser Stille wurde eine geöffnete Attraktion. Die Regel liegt jetzt in `statusWithoutLiveData` (API). `isCurrentlyInSeason` hat **drei** Werte und der dritte ist der Punkt: `false` schließt, `true` ist offen, **`null` verhält sich exakt wie vorher** — es heißt „saisonal, sonst nichts bekannt" und darf keine Bahn verstecken, die wir bloß noch nicht verstanden haben. Dort sitzen die meisten: der Detector nennt für alles unter 330 Beobachtungstagen bewusst keine Monate. Also überall `!== false`, nie `=== true` (`lib/utils/season.ts`). Eine Live-`OPERATING`-Zeile schlägt trotzdem alles: sie ist eine Beobachtung, die Saison eine Beschreibung von Vergangenem. Dasselbe gilt für den Zähler: **„12 von 45 geöffnet"** ist eine Aussage darüber, wofür man sich heute anstellen kann, und eine Bahn, die vor November gar nicht aufmachen kann, gehört weder zu den 45 noch zu den 33 geschlossenen. Denselben Satz rendern **vier** Quellen, drei davon SQL über den ganzen Katalog ohne je eine Zeile zu laden — dafür gibt es `attractionIsOutOfSeason()`, den SQL-Zwilling der TS-Regel, nach dem Vorbild von `scheduleRowSpeaksForToday()` und gegen einen echten Postgres über alle 300 Spaltenkombinationen geprüft; handgeschriebener Zwilling, also ändert man beide Hälften oder keine. Auf dieser Seite blendet die **Pre-Mount-Übersicht** die Bahnen jetzt genauso aus wie die Karten daneben — sie ist das einzige Attraktions-Markup ohne JavaScript und listete sie direkt unter dem Zähler, der sie weglässt —, und der Badge sagt **„Nur im Winter"** statt zweimal „Winter" in zwei Deckkraftstufen. Strukturierte Daten behalten sie: `containsPlace` sagt, was der Park enthält, und das ist ganzjährig wahr. Ist der Detector schlicht im Unrecht (lange Umbaupause sieht von außen aus wie eine Saison), ist das eine Kuration unter `/admin/attractions/<id>` — **Saisonal** und **Betriebsmonate**; existiert die Bahn gar nicht mehr, ist daneben der **Status**. See [seasonal attractions](docs/api/seasonal-attractions.md).
**Weather day chart is built around the park's hours (REQUIREMENT):** the hourly chart's time axis is **piecewise linear, not linear** — an open hour is drawn 4× as wide as a closed one, which takes the median park's opening hours from 42 % of the width to 74 % and is what makes room for hour-by-hour ticks and a few temperature readings inside the visit. Both kinks sit **exactly on the dashed borders of the opening-hours band**: a change of slope the eye cannot account for reads as weather, so it has to land on a line that is already there and is labelled with the opening time. Parks with no OPERATING row for today (about a quarter of the catalogue on any given day) keep the exact linear axis they had — `buildDayScale` returns `null` and every formula reduces to the old one, which the unit tests assert. Geometry is pure and lives in `lib/utils/weather-chart-axis.ts` (`pnpm test:weather-chart-axis`), never in the component; it works in a continuous **point index**, never in hours-since-midnight, because a DST day has 23 or 25 points and `points[i]` is then not the `i`-th hour. The chart owes the card **143 px** whatever it draws (`h-28` + `mt-1` + a fixed `h-[27px]` axis), so every tick and label is out of flow and `whitespace-nowrap` — as a flex row of 24 equal cells the German labels wrapped and it came out 154.5 px against a 143 px reservation on every phone. Tick density is a **container query** on the chart, not a `sm:` breakpoint: `/ui` renders this card three to a row, so a 355 px chart at a 1280 px viewport would otherwise get a desktop's worth of labels. See [weather day chart](docs/features/weather-day-chart.md).
**The admin holds no credential (REQUIREMENT):** `/admin` authenticates with an **httpOnly session cookie** — client code sends nothing, `adminFetch` is a plain same-origin fetch, and `app/api/admin/[...path]` turns the cookie into `Authorization: Bearer …` server-side. The shared password in `sessionStorage` it replaced was readable by any script on the origin and unlocked every administrative endpoint on api.park.fan, which until this change had **no guard of its own at all** — the `?pass=` it advertised was checked by a Cloudflare rule and by nothing in the application. Four things in the proxy are load-bearing and were each a bug before: it must export **every verb** (the editing API uses PATCH and DELETE, which 405'd at Next), it must not call `response.json()` unconditionally (a 204 from a logout or a delete threw), it must move a re-issued token from a password change into the cookie — passing it through would leave the browser holding a cookie that was just revoked, i.e. logged out by succeeding — and it must **validate** that cookie against `auth/me` rather than notice one is set, because reading a cookie back only proves the caller can send a header: `Cookie: parkfan_admin_session=x` satisfied the gate written to keep strangers away from `getServerApiHeaders()`'s `x-auth-key`, the header the API reads as "this is our own frontend" and therefore as licence to skip the throttler and to trust the forwarded address. Not `requireAdmin` though: the password change and the TOTP enrolment are behind this proxy and a session owing either must still reach them, so the role floor stays where the API enforces it. The deprecated `pass` query parameter is dropped rather than relayed. The login form carries the **same Turnstile challenge `/contribute` uses** (widget now `components/common/turnstile-widget.tsx`, verify `lib/security/turnstile.ts`), checked in `/api/admin/session` **before** the credentials are forwarded — everything behind it only counts attempts that were already made, and the per-account lockout is a weapon pointed the wrong way, since anybody who knows an editor's address can spend their five tries and keep them out. A token is **single-use**, so a two-factor login solves twice and the form resets its widget in the `finally` of every attempt; a missing secret in production is a hard failure, so an unset `TURNSTILE_SECRET_KEY` locks the admin out rather than leaving it open. **`success: true` is not the answer to „may this proceed"**: Cloudflare confirms a token is genuine and says nothing about which form it was solved on, so the **action** (`TURNSTILE_ACTIONS`, its own `server-only`-free file so widget and check share it across the client boundary) and the **hostname** (`TURNSTILE_HOSTNAMES`) are checked too — `/contribute` shares this widget and is a challenge anybody may solve as often as they like, so without the action check the upload form is a token vending machine for the admin login. The two unconfigured cases are asymmetric on purpose: a missing secret refuses in production, a missing hostname allowlist **skips** its check, because an unset variable must not be able to take both forms down on the deploy that shipped it (`pnpm test:turnstile`). **This side is not the only side:** `/v1/admin/auth/login` is public, so a bot skipping this app never meets the challenge — the API asks for a solved token from every caller that does _not_ send a valid `THROTTLE_BYPASS_KEYS` value, and this app is exempt because it already redeemed the token (single-use), which is also why the API cannot be the only verifier without a lockstep deploy. The second-factor step **looks like six boxes and is one input** — the boxes are drawn and a transparent field lies over the row. The six real inputs it replaced could not be autofilled and it was one line: `value.replace(/\D/g,'').slice(-1)` per box is right for a person typing one digit and wrong for 1Password, which writes all six characters into the first box in a single event — the slice kept the last of them, so a fill produced a lone `6` and five empty boxes, with no error anywhere. `autocomplete="one-time-code"` belongs on one field, a `readOnly` username rides along hidden on that step (the e-mail input is gone from the DOM by then, and a manager with nothing to match on offers codes from every item that has one), and a complete code submits itself, because six pasted digits behind a button save nobody the typing. The curated-field editor is **generated from backend descriptors**, so a new curated column appears with no frontend change; two of its controls exist for a reason — a curated height of `0` means "no minimum at all" and empty means "accept upstream", and a curated boolean has three states because a curated `false` is a real correction. Media and blog stay a separate write model (files → pull request), which is why the entity media panel is a view with links rather than an editor. See [admin](docs/features/admin.md).
**The header menu is three kinds of content, and the split is about the link graph (REQUIREMENT):** everything the full-width band renders is a link on ~35,000 pages, so the parks panel server-renders **continents and countries only** — 28 hub links, 420 B brotli, all 23 countries visible at once now that the band is container-wide (the first version swapped country lists with four of five on `display:none`; going full width deleted that state). The 144 cities and 212 parks under them are fetched per opened country from `/api/nav/geo/[continent]/[country]`: they are already reachable from those hubs and from the sitemap, so putting them in the template would spread the same weight over 356 more targets and buy no discovery. The **photo rail is a fixed six**, not a thumbnail per park — the media database holds a picture for **14 of 212 parks** — and it reuses the homepage's per-locale `FEATURED_PARK_SLUGS` intersected with the parks that have one, resolved in the layout because `@/lib/media` is the 107 KB catalog and the header is a Client Component. **Hover has to be rested on, not crossed**: the detail row sits under the country columns, so the way to it leads over the countries below — entering a row only arms the switch and leaving before 140 ms disarms it (focus commits at once). That same gesture used to break the fetch, and it was one bug: the effect discarded its response on cleanup while leaving the key in `requested`, so skimming past a country threw its answer away and the guard then refused to ask again — **23 of 23 countries stayed empty, 0 of 23 after**. A response keyed by country is a cache write and is correct whenever it lands, so nothing cancels it; a failed request drops its key so the next hover retries. Same rule shaped the blog panel: 3 categories and the 4 newest posts with their covers in, **31 tags out** — 31 tag pages over 7 posts are mostly one post's teaser at a second URL. The band is **glass, not opaque** (`bg-popover/95` + `backdrop-blur-xl` + the popover ring): flat means no pointer-depth tilt, not no blur, and `/80` let a park page's headline and body text read straight through the menu. That glass is also why the opening animation (`lib/hooks/use-menu-reveal.ts`) only ever targets **descendants** of the surface: a transform or an opacity on it, or on any ancestor, makes it a backdrop root and the blur goes flat exactly while somebody watches it appear. Same split as the header's own reveal — CSS owns visibility (a `hidden` class), GSAP animates `y` and never `opacity`, and under `prefers-reduced-motion` the chunk is never even imported. It is positioned against the `<header>`, not the trigger — centred on an entry 276 px from the left edge a 700 px panel starts at −36 px — and carries `overflow-hidden`, because the rows' `-mx-2` bleed gave the document a horizontal scrollbar at exactly 1024 px. Watch two traps: a single `useTranslations('blog')` in a header component pulls the whole namespace into the layout chrome that **every** page serializes (6066 B → 9047 B × 6 locales, for one label — the word lives in `navigation` now), and the bar has **one** breakpoint, not two: the nav used to start at `md` while the search input waits for `lg`, so 768–1023 px carried the full nav plus a 256 px search button plus no burger, 789 px of content in a 736 px box, wrapping German onto two lines with a horizontal scrollbar. Measured cost of the whole menu: **+5.65 KB brotli per page** (~4.2 of it the 23 flags) for 4 → 48 crawlable nav links, all resolving 200, CLS unchanged, and zero photo requests until somebody opens it. See [header navigation](docs/features/header-navigation.md).
**The guide page teaches the real cards with the ride's real numbers (REQUIREMENT):** `/{locale}/{howto-segment}` (`app/[locale]/how-park-fan-works/`, localized slug in `lib/howto/segments.ts`, the old `/howto` 301s per locale, bare `/howto` deliberately left to the middleware so it lands in the reader's language) answers „was macht diese Seite, was ein Wartezeiten-Feed nicht macht“, so every block renders a **production** component — `AttractionCard`, `AttractionTypicalWaits`, `RopeDropCard`, `ParkCalendarDay`, `NoLiveWaitTimesNotice` — and every figure in it is a value the API actually returned, dated in `_fixtures.ts`. A redrawn lookalike defeats the exercise and starts lying at the first restyle; an invented number is worse, because the block next to it links to the ride's own page. **Audit before you claim**: `AttractionTypicalWaits` prints the weekday's **P90** above each bar and no measured-day count (its hint names the _window_, not the sample size), and **no surface anywhere puts sample days next to a ride** — `ParkStatsAttractionsCard` renders rank/ride/(now)/P50/P90, and the count exists only in the stats section's subtitle, the `Tage` column of the by-month and by-weekday cards, and the blog's `ride-waits-widget`; four sentences claiming a per-ride column on the park page shipped in German and were translated into five more languages before anyone read them; `typicalWaitThisHour`/`currentVsTypical` exist on the payload and are rendered **nowhere**; the calendar reaches a year out only for year-round parks, while a seasonal one returns CLOSED past its published season; and „früh kommen“ is a per-ride finding, not a rule — Taron's day is flat (60/60/54/53/59 by hour) where Chiapas climbs 22 minutes. The thresholds are visible in one park: Colorado Adventure saves 40 off a 50-minute peak and gets no rope-drop tip against the ≥60/≥45 gate. **A displayed wait time is always a multiple of five** — parks post them that way, so every raw observation is, and what breaks it is the maths on top: `PERCENTILE_CONT` interpolates between two stored values and `AVG()` across days blurs the rest, which is how the hourly table printed 51, 53 and 47. The API rounds on the way out and `roundWaitTo5` (`lib/utils/wait-time.ts`) does it again at render, so a surface is right whichever build answers. **Round only what is displayed**: a crowd ratio, a ranking, a colour tier and the pick of a ride's peak hour all read the raw value, or five-minute buckets invent ties the data does not have — rounding first moved Wodan's peak from 12:00 to 11:00 and broke a test. And a **difference** is not a wait time: `roundWaitTo5` floors everything under 2.5 to zero because no queue is −15 minutes long, so pointing it at the attraction card's trend delta deleted the whole falling half of the scale and every shrinking queue on every park page rendered „stabil" — visible on the guide itself, where Black Mamba sat at a grey „Stabil" under a caption saying its queue was being worked off. Signed deltas go through `roundWaitDeltaTo5`. Two live blocks are exceptions to the frozen-fixture rule (`LiveHourlyProfile`, `LiveTopAttractions`): where the point is „das läuft gerade", a frozen copy is the wrong exhibit, and the prose beside them names no figure they render. Two fixture anchors: the queue history, best-visit slot and rope-drop instants come from `getServerNowMs()` because a card's sparkline stretches its axis to the reader's clock and a hard-coded date decays into a flat week-long tail, while the rope-drop instants are wall-clock times in the **park's** zone. Motion follows `use-menu-reveal`'s split plus **no ScrollTrigger**: `WaitScaleBar` is a server-rendered `<figure>` whose geometry is three CSS custom properties, an `IntersectionObserver` picks the step and GSAP only tweens between two readings. Two traps the visuals cost: `Sparkline` fits each instance to its own max, so two charts meant to be compared need the shared `yMax` prop or the flat one is drawn as dramatically as the steep one; and the wide decorative layers (sign glow, `Ambience`) must be clipped with **`overflow-x-clip`**, never `overflow-hidden`, which would make the element a scroll container and stop the sticky figure pinning. Structured data is Article + Breadcrumb + `FaqList`'s `FAQPage`, never `HowTo`. All six locales ship the guide as a full `content/<locale>.tsx` with localized chapter ids, the same per-locale-module convention as `fancast` — so an edit lands six times, and two greps guard it: `CHAPTERS` must match the rendered `<SectionShell id= index=>` calls exactly, and each file's `locale=` prop on the two live blocks must be its own. See [the guide page](docs/features/how-park-fan-works.md).
**A chapter opens the same way everywhere (REQUIREMENT):** one component draws every chapter header on the site — `ChapterHeading` (`components/common/chapter-heading.tsx`): oversized translucent glyph, optional kicker, title, closing rule. The guide page reaches it through `SectionShell`, a blog post's `##` through the h2 renderer in `blog-content.tsx`, ride pages through `PageSection` → `SectionHeading`, park pages directly. There were **five** before, three of them on one park page — `text-xl font-semibold` with an icon, `text-xl font-bold` with an icon, a `text-2xl` frosted pill, a bare `<h2 class="text-xl font-bold">`, `GlassSectionTitle` — and nothing told a reader which of them opened a chapter and which labelled a card inside one. `GlassSectionTitle` stays, for the band _inside_ a page (homepage favourites, the nearby-parks list): it is not a chapter header. Three decisions sit in the component so a call site cannot get them wrong. **A number must not skip:** a post's chapter numbers come from `extractToc(markdown)` and never from a counter incremented while rendering, because the body is split into one `<ReactMarkdown>` per widget fence and a render-time counter restarts at each one (01, 02, 01, 02); park and ride chapters carry **no** number for the same reason, since `NearbyParksSection` renders nothing for 48 % of parks. **An icon standing in for the number is drawn at `/25`, not `/15`** — the numeral is solid and survives 15 %, a hairline Lucide icon disappears. **`frosted` is a full-width band, not a `w-fit` pill**, because park and ride pages sit on an arbitrary photo and a watermark over the bright part of one is unreadable; the heading's own `border-b` is the band's lower edge. And the height moves when a title wraps, per locale and per breakpoint, so both streamed chapters render the **real** heading while loading — `ParkBestDaysHeader` and `ParkStatsHeader` exist as their own files so the placeholder can mount them with only the data-dependent hint replaced by a `Skeleton`. `SectionHeading`'s `plain` variant is unchanged and is still what belongs **inside** a card. See [design system → chapter headings](docs/design/design-system.md#chapter-headings).
**Reuse existing components (REQUIREMENT):** always reuse existing components (e.g. `ParkStatusBadge`, `CrowdLevelBadge`, `Badge`, `ParkCard`) instead of re-implementing UI inline — keeps styling/colors consistent. Only build new when nothing suitable exists. See [conventions](docs/development/conventions.md#11-reuse-existing-components).
**The header is 48 px, and its height is written down in four places (REQUIREMENT):** `h-12` on `<header>` (the inner container is `h-full`, never a second copy of the number), the `<Suspense>` fallback in `app/[locale]/layout.tsx` that reserves the bar while the client `Header` streams in, and `-mt-12` on the three heroes it floats over (homepage, blog post banner, editorial hero). Miss the fallback and every page opens with a shift of the difference. Control heights come off the button scale in `components/ui/button.tsx` (`sm` 32 / default 36 / `lg` 40), not out of the air — the old bar put the **largest** of them, the 40 px `lg` search field, in the shortest row in the app at 71 % of a 56 px bar. And the logo is **one component rendered twice**, never two sets of classes: on a hero page the header parks a copy in the corner and keeps one in the flex flow, then cross-fades them while sliding one onto the other, which only reads as a single object if they are congruent. They were not — `h-7 md:h-9`+`h-5 md:h-6`+`gap-0.5` against `h-6`+`h-5`+`gap-1` made the handoff animate a 1.5× scale, and no single factor can reconcile a pin:wordmark ratio of 36:24 with 24:20, so the corner copy stayed 15–25 px wider than the bar copy the whole way across (measured at 1440). `BrandLockup` is the fix and the guarantee: `logoScale` resolves to 1.000, the handoff is a pure translate, and per-frame sampling puts the two boxes 0.0 px apart on all four edges. See [design system → header geometry](docs/design/design-system.md#header-geometry).
**three.js animations (REQUIREMENT):** research the real-world reference **first**, then implement; and **verify every animation from all camera perspectives** (coaster player: Front, Follow, Onboard) across the whole timeline and both day/night themes via the headless render harness (`node scripts/render-coaster-elements.mjs`) before shipping — a green build is not enough. See [conventions](docs/development/conventions.md#12-threejs-animations-research-first-then-verify-from-every-perspective-requirement).
**Ride ↔ Glossary link:** rides carry a curated `rideProfile` from the API (track figures **in ride order**, ride type, builder) stored as **glossary term ids**, so the ride page links into the glossary (`RideProfileSection`) and each term page lists the rides that feature it (`GlossaryTermRides`). Element order is meaningful and repeats are intentional — never dedupe or sort it. **This app is the only place a term id is defined** — the API's mirrored allowlist is gone, so nothing validates them and a renamed term silently shortens every ride layout that used it; check the API's `attraction_ride_profiles` rows before renaming or removing one. See [glossary](docs/features/glossary.md#ride--glossary-link).
**Nothing here has a reader inside the site (REQUIREMENT):** the machine-facing surface — `/robots.txt`, `/llms.txt`, `/auth.md`, the four documents under `/.well-known/` (`api-catalog`, `agent-skills`, `ai-catalog.json`, `mcp/server-card.json` — two carry the extension and two do not, so the list is spelled out: typing the wrong one is a 404), the homepage `Link` header, `/api/mcp` and the WebMCP tools — is the only part of this app that **no page renders**. It can rot through a green build and every passing suite, and the first symptom would be an agent getting a 404, which is why `pnpm check:agent-ready` and `pnpm check:webmcp` fetch all of it from outside (a running site) and why a new document belongs in that script in the same commit. Everything it describes lives in `lib/agents/`, and the reason is always the same: **two copies of one claim, one of them invisible.** The `Link` header and the catalog document name the same URLs, so a URL fixed in one and forgotten in the other keeps pointing at a 404; the skills index publishes a **SHA-256 of the bytes served**, computed at build time from `content/agent-skills/<name>/SKILL.md` and never written down beside the file, because an agent is entitled to check that digest and throw the skill away; the MCP server card lists the tools by asking the server for them. Same rule one layer up: the browser's WebMCP tools **call `/api/mcp`** rather than the API, because the rules an answer depends on sit with the data. Two of them are absolute. A park with **no wait-time source** aggregates to Ø 0 minutes over an empty set and is byte-for-byte a park shut for the night — the tools read the curated flag through `noLiveWaitTimesReason()` and answer `waitTimesAvailable: false` with a sentence, and the check asserts exactly that against Hansa-Park; a ride **out of season** is reported by `effectiveStatus`, never the raw `status`. The policy is three questions, not one: `Content-Signal: search=yes, ai-input=yes, ai-train=no`, repeated per crawler because a bot reads only its own block — a training corpus gets `Disallow: /`, a fetch made while a person waits gets what a search engine gets, which is Cloudflare's own Search/Agent/Training split. The same three answers ship a second time as an **RSL licence** at `/license.xml` (`License:` in robots.txt, `Link: …; rel="license"` on every localized page — the one header here that is deliberately not homepage-only, because the audience for a licence is the crawler that skipped robots.txt), and the Content Signals preamble is **Cloudflare's text copied verbatim**, down to the Article 4 EU-copyright reservation: a reworded legal notice is a different legal notice. Two things stay outside the repo on purpose — enforcement (Cloudflare AI Crawl Control) and the markdown negotiation that answers `Accept: text/markdown`, which is an edge conversion, so nothing in this codebase renders it and the check reports it instead of asserting it. And **`/admin` is in none of it**: robots.txt, an `X-Robots-Tag` on the response (the JSON routes under `/api/admin` render no meta tag), the layout metadata, and the navigation tool's own refusal — four fences because each stops a different visitor, and the tool is the only one an agent could otherwise walk through. Two scanner checks stay red on purpose: DNS-AID is a DNS change, and an A2A agent card would describe an agent that does not exist. See [agent readiness](docs/seo/agent-readiness.md).
**A `<lastmod>` is observed, never stamped (REQUIREMENT):** Google ignores `changefreq` and `priority` outright, so until the content-change crawl existed the attraction sitemaps carried **42,756 URLs and no signal at all**, and the main one dated 1,662 of 3,480 — the glossary and the blog, the two things that are files in this repo with a date on them. The API has no per-entity content timestamp (`/v1/sitemap/attractions` answers `{url, slug}`; a park payload dates only its live readings), so the date is **observed**: a daily 05:30 UTC run fingerprints the _stable_ half of every park and ride, and the day the fingerprint moves is the day the page changed (`lib/seo/content-changes/`, snapshot in Vercel Blob because it has to outlive both a deploy and an ISR regeneration). **The whole value is in what stays out of the hash.** A park page repaints every five minutes, so `queues`, `status`, `crowdLevel`, `statistics`, `typicalWaits`, `bestVisitTimes`, `ropeDrop`, `isHeadliner`, `isCurrentlyInSeason`, `weather`, `schedule` and `analytics` are excluded by hand — let one of them in and all 44,000 URLs change every morning, which is a build stamp, and one identical value everywhere is exactly what gets a sitemap's lastmod discounted, taking the glossary's and the blog's honest dates down with it. In goes what a reader sees and what stays put: name, land, height limits, the ride profile with its glossary terms, the curated park facts, the media versions and the blog backlinks. Three rules are load-bearing and each fixed a real hole: a park the API did not answer **keeps its dates** (`retainUncovered`), because dropping it re-adds its rides tomorrow and a re-add reads as a change — one timeout would be 82 false recrawl invitations; a **`FINGERPRINT_VERSION` bump** adopts the new hashes and keeps every date, since editing the detector is not the catalog changing; and which rides count comes from `getAttractionPaths()`, the sitemap's own list, not from re-deriving the variant-slug rule against the park payload — the two disagree on seven rides, which was seven `<lastmod>` values for URLs no sitemap lists. The same snapshot feeds IndexNow, which used to submit all ~46,000 URLs every morning and now sends the paths that moved (Mondays still sweep everything, so a detector that stops detecting cannot silently mute the route; `?dry=1` builds the list without sending it). `pnpm test:content-changes` pins the blindness and the three rules, because a green build shows none of it. See [sitemaps](docs/seo/sitemaps.md#lastmod-observed-not-stamped).
**A feed nobody links to is a file with a URL (REQUIREMENT):** the six blog feeds (`/{locale}/blog/feed.xml`) existed for as long as the blog did, and the discovery link that makes them reachable was spelled out by hand in four `page.tsx` files — so the **category pages**, added later, had none, and neither did the homepage, where a reader looks first. It cannot be fixed centrally: **Next replaces the whole `alternates` object at the nearest segment that declares one** instead of merging into it, proved by `contribute/thanks`, which sets only `canonical` and ships zero hreflang links though the locale layout declares `languages` — and all 25 locale routes declare their own. So every route carries it, through **`blogFeedAlternates(locale)`** (`lib/blog/feed.ts`), which returns the whole `types` object so a call site cannot half-build it, `undefined` where the locale publishes nothing (the route 404s there and a broken feed is recorded against the site, not the locale), and the **array-of-descriptors** form because a bare string carries no `title`. Park and glossary pages get none on purpose: the spec wants a page's own main feed. And the `<head>` was never the whole job — the link was on `/en/blog` all along and **no page rendered one a person could click**, so the footer now does, inside the same `showBlog` guard the feed 404s under. In the items, **a widget fence must never be rendered into the feed**: a reader archives an item on arrival and never re-fetches it, so today's numbers would sit frozen in every subscriber's client forever, which is the exact thing the fences exist to prevent — each becomes a link to the live table, in place, because the prose around it refers to it. `ref:` links resolve through **`resolvePark` only** (a ride URL is its park's href plus the slug; `resolveAttraction` would cost 425 KB per ride for a URL), and `react-markdown` needs its `urlTransform` overridden or every one of them arrives as `href=""`. Three old bugs are pinned by `pnpm check:agent-ready`: `lastBuildDate` came off `posts[0]` of the **featured-first** `listPosts`, so pinning an older post moved the channel's timestamp backwards; items ended with `<readingTime>` in no namespace plus a `<source>` naming this feed, i.e. every item claiming to be a repost of itself; and every `<enclosure>` said `length="0"` — it is measured off the file now, never from the media database's `bytes`, which describes the **source** photo and not the crop a cover usually is (89 KB against 290 KB for Voltron). WebSub is two halves and both are load-bearing: the feed declares the hub, and `/api/cron/websub` (plus `pnpm ping:websub` for the minutes after publishing) tells it to look — a declared hub that is never pinged is exactly as fast as polling. See [blog feeds](docs/seo/blog-feeds.md).
**Umami event budget (REQUIREMENT):** Umami Cloud bills **every event property as another event**, so a 5-property event costs 6× a pageview and the plan (100k/month) is blown by properties, not traffic. Before adding one: never send what Umami already has (URL, referrer, `navigator.language` → so no `locale`, no `path`) and never send what a sibling property implies (`in_park` was `type === 'in_park'`, `hasQuery` was `queryLength > 0`). Events firing on **load** cost their property count on every pageview — price them accordingly. Keep `data-exclude-hash="true"` on the script tag: the tracker patches `replaceState` and bills a changed hash as a fresh pageview, which the park tabs and the calendar month stepper both write. See [analytics](docs/development/analytics.md).
**No text may read as AI-generated (REQUIREMENT):** this covers **every** string a human ever sees, not just blog posts — and the tell that survives every other pass is **the aphoristic closer**: a short, symmetrical, abstract sentence parked at the end of a post, a section or a landing band, restating what was just said as a maxim. Three shipped and had to be pulled — „Sie ist nicht die Antwort. Sie ist die Frage.", „Such dir einen Park und lies eine Zahl." and a `title="…"` that was two imperatives joined by „und". Grep the closing sentence for `ist nicht … sondern`, for `Sie ist nicht X. Sie ist Y.`, and for a concrete thing (a wait time, a queue) standing in for an abstract one (an answer, a promise). The test: cover the last sentence and re-read — if only a _feeling of closure_ is lost, it was decoration. End on the concrete next action with its specifics, on a fact not yet stated, or simply stop. **Never narrate the sign at the entrance** — no `das Schild`, `the sign`, `het bord`, `le panneau`, `el cartel`, `il cartello`. It is a prop the copy kept reaching for to carry an argument, and it multiplies: by the guide's launch it stood in the hero caption, the scale legend, the figure's screen-reader summary, a chapter-01 paragraph and the companion post, six locales deep — one picture retold five times. Name what is actually there: `am Eingang stehen 70 Minuten`, `At the entrance it says 70 minutes`. Second rule from the same review: **copy must not describe the page's own layout** — „Links steht … Rechts …" was wrong on every phone, where the panels stack, and „die letzte Stufe rechts" sat beside a `flex-wrap` badge row. Vertical order is usually safe, horizontal order almost never — image `alt` and `caption` in the media sidecars, UI copy, PR bodies, commit messages, docs. The tells to avoid are structural, not just lexical: the same sentence skeleton repeated across a set (subject + participle clause + "behind it / in front of it"), an exhaustive inventory of everything in frame, mood adjectives nobody asked for (`bathed in`, `against a summer sky`, `sweeping the night sky`), and a caption that restates the alt text. Write what a person would write: **alt** is short and factual, for somebody who cannot see the picture; **caption** is what you would say pointing at it, and is allowed to be a fact, a joke or nothing. Vary the shape between neighbouring entries — six captions in a row starting with the ride name is itself the tell. Details and the do/don't table for prose: [blog authoring guide](content/blog/README.md#8-writing-style-requirement); for image text: [public/media/README.md](public/media/README.md).
**Blog writing style (REQUIREMENT):** posts must not read as AI-generated. **Never use „ehrlich" in any form** (`ehrlich gesagt`, `der ehrlichste …`, `um ehrlich zu sein`) — it is the clearest tell — and avoid the register around it: no `bezahlte Vorfahrt`, `Datenpunkt`, `die These dieses Artikels`, `X-Währung`, `Fairness-Hinweis in eigener Sache`, no announcing the article's own structure, no unsourced superlatives, and **no em dash `—` in running text** (wrong character in German anyway — use `–`, a comma or a full stop; the only `—` in a post is the `— Patrick` signature). German grammar counts too — check the article before "correcting" one in (it is **das** Efteling, like `das Toverland` and `das Phantasialand` → `bis zum Efteling`, `im Vergleich zum Efteling`, but `das Efteling ist …` — never `der`/`die`). Full do/don't table + voice reference in the [blog authoring guide](content/blog/README.md#8-writing-style-requirement).
**A wait time is never typed into a post (REQUIREMENT):** four articles carried **22 hand-maintained tables across six languages** — a park's top ten, rides compared across parks, weekdays, and Europa-Parks 8 × 10 hour matrix, eighty numbers per locale. They had already drifted with nothing to detect it: the Efteling post said 34 minutes for Joris en de Draak while the park page said 35, and two tables in one Toverland post disagreed by a minute because they were typed a week apart. Every such table is now a fence — `ride-waits-widget` (`park=`+`top=` for a ranking, or a semicolon-separated `rides=` list across parks; **semicolons because a build type holds a comma**) and `hourly-profile-widget`. What stays in the post is what does not move: a coaster's `|Label` and `|Type` are stable facts, the minutes never are. The split between the two modes is about what the table claims — `park` mode is ranked by the data because **the ranking is the claim**, `rides` mode keeps the author's order because the sentence under it depends on that order, and only `rides` mode applies a 60-day floor, because setting two numbers side by side invites subtracting them while a ranking has a `days` column that states each row's basis. And **a sentence next to a widget must not name a figure the widget renders** — write the shape ("gut eine halbe Stunde", "ab Mittag etwa die Hälfte"), which stays true while the number moves. Fetching is centralised in `useParkStatsQueries` (query key, stale window, `useLoadLast` gate) so two tables about one park share a request; `topN` is a **closed set** at the proxy because it lands in the CDN cache key. The hourly table needed a backend projection first: `/stats/hourly` answers eight rides in ~2 KB where the attraction endpoint costs 425 KB, 45 % of it a `schedule` nobody renders. See [blog widgets](content/blog/README.md#6-live-widgets-code-fences) and [API budget](docs/architecture/api-budget.md#blog-widgets-what-a-post-may-fetch).
**The quietest weekday may be two days, and a thin day drops out rather than ending the vote (REQUIREMENT):** the best-travel-time hub showed an em dash for **3 of 6** featured parks, correctly by the old rules and wrongly all the same. A weekday measured far more rarely than the others used to refuse the whole park — Movie Park has 13 Mondays against 23 Sundays — when dropping that one day leaves four comparable ones that do say something; and a tie counted as "cannot choose" when Disneyland Paris measuring 32 minutes on Sunday **and** Wednesday means the park has two quiet days, not none. Both days are named now. Measured across the eighteen parks this table is ever asked about: **12/18 filled → 17/18**, with no park that already had an answer getting a different one. Three refusals remain and each fired on a real park: fewer than four evenly-measured weekdays left, three or more days sharing the minimum (Disney Adventure World reads 39 on four of them — a park with no quiet day), and a "quietest" day not actually below the park's own median. In the same card the **park name is never the cell that gives way**: `table-layout: auto` hands width to the widest unbreakable content, so `max-w-0` on the park column collapsed it to "Europa-P…" while "34 Min. · Voltron Nevera powered by Rimac" kept all 39 characters. The name is the row's subject, a ride name a detail of one column — `w-full max-w-0` moved to the longest-queue cell instead. Same trap one layer over in `RideWaitTable`: the ride column may only claim the slack when it is the **only** text column, or park and type collapse to "Ph… Mult…" beside 500 px of empty name column.
**Park/Ride page ↔ blog link:** park pages list the posts about that park, ride pages the posts about that ride (`ParkBlogPostsSection` / `AttractionBlogPostsSection`, reverse index in `lib/blog/backlinks.ts`). The relation is derived from the post itself (`ref:`/widget references, a ride counts for its park too, plus `relatedParks`/`relatedAttractions`), so a round-up like the Halloween guide lands on all ten park pages without a list. `parkLinks` / `rideLinks` in the frontmatter override it (`false` = never, or an explicit list; `rideLinks` also takes `parkSlug/*`), are **independent of each other** and are resolved **per post, not per locale** — setting one in any language governs all six, and `pnpm generate:blog-manifest` warns when translations disagree or an entry isn't a valid slug. See the [blog authoring guide](content/blog/README.md#the-other-direction-park-and-ride-pages-linking-back).
**Media database (REQUIREMENT):** every image — park, ride, blog, diagram — lives in ONE filesystem-backed database at `public/media/<collection>/`, with a `<name>.json` sidecar per image. **A collection is storage, the sidecar is the index:** nothing queries by folder, so a Halloween photo of Troy sits in `toverland-halloween` and still answers `getRideImages('toverland','troy')`. Never infer park/ride/role from a filename or folder. Read from `@/lib/media` (structure + search), `@/lib/media/text` (localized alt/caption — 37 KB, import only where text is rendered) and `@/lib/media/hero` (**the only client-safe one** — importing `@/lib/media` into a Client Component ships the 107 KB catalog). Image URLs carry `?v=<content hash>` because retargeting a focal point rewrites a crop's bytes at an unchanged URL; `images.localPatterns` in `next.config.ts` is what permits that query. `focus` is one point per image driving BOTH the CSS `object-position` on every card/background AND the offset the build-time 16:9/4:3/1:1 crops are cut at. Authoring contract: [public/media/README.md](public/media/README.md); full docs: [media database](docs/features/media-database.md).
**One photo can index two rides (`alsoRides`):** the API lists Winja's Fear/Force and YOY Chill/Thrill as two attractions each, but the park built one structure and the photo is genuinely of both. `ride` holds one slug, so these used to be stored as two byte-identical files — and when the media migration removed the duplicate, the second ride silently lost its only picture (no error: nothing re-checks whether a ride still has one). `alsoRides` names the further rides a photo answers for, matched by `getRideImages`/`getRideImage`/`searchMedia` and by the `ride-card` uniqueness audit; every slug is validated against the park's attractions, so the next typo is a build warning instead of another blank ride page. It is the `ride` counterpart to `roles` carrying two entries (`symbolica.jpg` is `park-background` **and** `ride-card`) — and not a licence to reuse: the photo must be a fair card for every slug named. See [public/media/README.md](public/media/README.md) and [media database](docs/features/media-database.md).
**Card photos are two layers (REQUIREMENT):** `object-fit: cover` scales to the **larger** of the two ratios it needs, so it overflows on one axis and fits exactly on the other — paint a photo across a whole card (405×404, aspect ≈1.0) and a 4:3 photo fills its _height_ exactly, leaving `object-position`'s Y with nothing to move. The focal point then renders byte-identical pixels however far you drag it, with a green build and no error. So the framing reference is the **strip between the glass panels**, not the card: `CardPhotoFrame` lives inside the card's photo-spacer row (405×220, aspect 1.84) and is what a visitor sees; `CardPhoto` still covers the whole card underneath so the frosted panels have something to blur. Same URL → one request, one decode. Where a card renders no bottom panel (ride with no live wait time) the spacer takes `row-span-2`, or the framed layer's lower edge sits exposed mid-card as a crop seam. Never widen the frame layer back to the full card. `pnpm check:card-framing` (needs a running site) asserts the box stays wider than 1.5. See [media database](docs/features/media-database.md).
**Blog manifest is split (REQUIREMENT):** the generator writes `manifest.ts` (frontmatter + build-time derivations, small) and `manifest-bodies.ts` (~900 KB of markdown). Galleries are no longer its job — they come from the media database. Import listings from **`@/lib/blog/listing`** — `@/lib/blog` drags every post body into that route's bundle, and it is imported by the root layout, the homepage and every park page. Body-derived values (reading time, `parkRefs`) are computed at build time by the shared `lib/blog/derive.mjs`, never a second copy of those regexes. See [scripts](docs/development/scripts.md#the-blog-manifest-is-three-files-on-purpose).
**Blog spotlight cards:** `ParkCard`/`AttractionCard` lay out via `row-span-3` + `grid-template-rows: subgrid`, so the row template must sit **on the card itself**, never on a shared wrapper that also holds the heading — `auto` tracks collapse against the panels' `-mb-4`/`-mt-4` and slice the title and wait time. Use `grid [grid-template-rows:auto_2rem_auto] sm:[grid-template-rows:auto_minmax(220px,1fr)_auto]`; the `2rem` absorbs that overlap once the photo is hidden below `sm`, and `minmax(220px,1fr)` keeps image-less cards full height.
**Localized blog gallery captions:** a gallery is a **collection** in the media database, and its captions live per image in the sidecar (`alt`/`caption` as `{de,en,nl,fr,es,it}`) — the old `captions.json` + five `captions.<locale>.json` files per folder are gone. A post may still override a caption inline; the same photo legitimately reads differently in two articles. See [public/media/README.md](public/media/README.md).
