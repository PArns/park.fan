# Translations are routed, not bundled (REQUIREMENT)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

everything handed to `NextIntlClientProvider` is serialized into the RSC payload — and the HTML — of every page that renders it, ×6 locales. So the locale layout ships **only the chrome** (`LAYOUT_MESSAGE_NAMESPACES`, ~6 KB) and each route adds its delta via `<RouteMessages route="…">` in its `page.tsx`. Both lists are **derived from the import graph** by `pnpm generate:route-namespaces` into the committed `i18n/route-namespaces.generated.ts` — never hand-edit it; after moving a component across the client boundary, re-run the generator. The merge happens **client-side** (`useMessages()` + `mergeMessages`) because a nested next-intl provider _replaces_ messages instead of merging them, so shipping the union would serialize the chrome set twice per page. A namespace that a route needs but doesn't ship does not throw: next-intl logs MISSING_MESSAGE and renders the raw key, which is why `pnpm check:client-messages` fails on a stale map, a missing wrapper, a wrong route key and a superfluous wrapper alike. Judge changes on the **compressed** number — the old flat allowlist looked like it saved 10 KB of JSON and was worth 2.3 KB after brotli. Namespaces only a cookie-gated section needs (`parks`+`attractions` for `FavoritesSection`) are declared in `LAZY_MESSAGE_BOUNDARIES` and **fetched** as a per-locale chunk instead, which requires the eager skeleton to keep reserving the same box so the swap costs no CLS. See [internationalization](docs/i18n/internationalization.md#which-namespaces-reach-the-client).
