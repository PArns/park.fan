# An ISR route needs both halves, and one of them is an empty `generateStaticParams` (REQUIREMENT)

One standing rule. It is indexed from the repo's [`CLAUDE.md`](../../CLAUDE.md), which carries the rule in one line and links here for the reasoning, the measurements and the counter-examples.

`export const revalidate = 86400` does not make a route cached. Two other things decide it, and each fails silently. **First, every fetch the route executes must carry `next: { revalidate }`.** Next 16 leaves an unqualified `fetch` at `no-store`, and one uncached fetch turns the whole route dynamic — the opposite mistake to the one [a `revalidate` at a call site](a-revalidate-at-a-call-site-is-somebody-elses-page.md) describes, and caught by the same walk of the route's import graph. **Second, a route whose segments are all dynamic and which declares no `generateStaticParams` is not registered in `.next/prerender-manifest.json` at all**, whatever its `revalidate` says: Next serves it per request and caches nothing. Measured on `/[locale]/parks/[continent]/[country]/[city]/[park]/average-wait-times` (2026-09-21): without the export the route was absent from `dynamicRoutes` and printed `ƒ` in the build table; with `generateStaticParams` returning `[]` it is `● … 1d` and `{"compute": "blocking", "fallback": null}` — nothing built ahead of time, each URL rendered on its first request and served from that render for a day. **Empty is the point**, not a placeholder: listing the 714 params would render all of them during `next build`, two API calls apiece, for pages that are cheap on demand and cached identically afterwards — the per-URL write explosion the park and attraction routes avoid by being `force-dynamic`. So the check is the manifest and never the route table: `ƒ` and "absent from `dynamicRoutes`" look the same from the outside as a route that simply has no prerendered paths yet. Prove a change by diffing `.next/prerender-manifest.json` before and after a build, the same artefact the `revalidate` rule is proven against.
