# Content packs

**Adding content must never require a core edit.** A ride, a shop, a scenery kit, a theme, a UI
icon set, a guest need and a scenario rule are all *declarations* — JSON manifests plus glTF —
registered through one API. If a thing cannot be added by dropping in a manifest, the module that
owns it has failed its gate.

Two packs ship, and they exist to prove the mechanism rather than to fill a catalogue:
`core-classic` (the default vocabulary) and `neon-lagoon` (a second theme with its own palette,
props, water tint, music bed and a ride type the first pack does not have).

---

## 1. Where a pack lives

```
app/game/_game/packs/
  core-classic/
    pack.json              manifest of manifests
    rides/*.json
    flat-rides/*.json
    coasters/*.json        track styles, car rigs
    scenery/*.json
    buildings/*.json
    shops/*.json
    themes/*.json
    scenarios/*.json
    strings.json           one file, all six locales, flat keys
  neon-lagoon/…
public/game/assets/<pack>/…  glb, ktx2, env, ogg — fetched, not vendored
```

A pack is `import`ed as JSON and registered at boot. That is the whole extension point: a new pack
is a folder plus one line in `packs/index.ts`, which is itself generated by
`pnpm generate:game-packs` from the folder listing — so in practice it is a folder.

---

## 2. `pack.json`

```json
{
  "id": "neon-lagoon",
  "version": "1.0.0",
  "name": { "en": "Neon Lagoon", "de": "Neon-Lagune" },
  "requires": { "engine": ">=1.0.0", "packs": ["core-classic"] },
  "license": "CC0-1.0",
  "provides": {
    "themes": ["themes/neon.json"],
    "rides": ["rides/*.json"],
    "scenery": ["scenery/*.json"],
    "shops": ["shops/*.json"],
    "scenarios": ["scenarios/lagoon-nights.json"]
  }
}
```

`requires.engine` is checked against `ENGINE_CONTENT_VERSION`. A pack asking for a newer engine is
**skipped with a visible notice**, never partially loaded — half a pack is worse than none.

## 3. Definition shapes

Every definition shares a head: `id`, `kind`, `name` (localized), `tags`, `theme`, `cost`,
`unlock` (research node or `null`). What follows is per kind.

### Flat ride (`kind: "flat-ride"`)

The rig is data. Animation is a list of **animated joints** with curve tracks, so a new flat ride
is a manifest plus a glTF — no code.

```json
{
  "id": "cc.chair-swing",
  "kind": "flat-ride",
  "model": "core-classic/rides/chair-swing.glb",
  "footprint": { "w": 14, "d": 14, "clearanceY": 12 },
  "capacity": 24,
  "cycleSeconds": 90,
  "loadSeconds": 45,
  "riders": { "minHeightCm": 110, "seats": 24 },
  "rig": {
    "joints": [
      { "node": "Hub",  "track": "spin",  "axis": "y" },
      { "node": "Boom", "track": "lift",  "axis": "x" }
    ],
    "tracks": {
      "spin": { "loop": true,  "keys": [[0,0],[8,360]], "ease": "linear" },
      "lift": { "loop": false, "keys": [[0,0],[12,26],[70,26],[85,0]], "ease": "inOutSine" }
    },
    "riderNodes": "Seat_*"
  },
  "ratings": { "excitement": 4.6, "fear": 2.1, "nausea": 3.4 },
  "power": { "kw": 45 },
  "cost": { "build": 78000, "runPerHour": 210 }
}
```

`ratings` here are the ride's **base**; a coaster's are computed from its layout instead.
`riderNodes` is a glob into the glTF node tree — the module parents guest instances to it, so seat
count and seat placement come from the model, not from a table that can disagree with it.

### Coaster style (`kind: "coaster"`)

```json
{
  "id": "cc.steel-looper",
  "kind": "coaster",
  "track": {
    "gauge": 1.6, "railRadius": 0.07, "tieSpacing": 1.2,
    "spineProfile": "box", "material": "cc.track-steel"
  },
  "car": { "model": "…/steel-car.glb", "seatsPerCar": 4, "carsPerTrain": [4,5,6,7], "mass": 1250 },
  "physics": { "frictionRolling": 0.0035, "dragK": 0.0021, "liftSpeed": 4.0, "launchSpeed": null },
  "pieces": ["straight","curve-l","curve-r","hill","drop","loop","corkscrew","banked-l","banked-r",
             "station","lift-chain","brake","block-brake"],
  "supports": { "style": "cc.support-steel", "maxSpan": 9, "footingRadius": 0.9 },
  "limits": { "maxGVertical": 6.0, "maxGLateral": 2.5, "minRadius": 6 }
}
```

`pieces` names entries in the shared piece library, so a new coaster style reuses geometry
generators and only declares which ones it may use.

### Shop / facility (`kind: "shop"`)

```json
{
  "id": "cc.churro-stand", "kind": "shop", "category": "food",
  "model": "…/churro-stand.glb", "footprint": { "w": 5, "d": 4 },
  "satisfies": [{ "need": "hunger", "amount": 55 }, { "need": "happiness", "amount": 6 }],
  "sells": [{ "sku": "churro", "cost": 90, "defaultPrice": 320 }],
  "staffSlots": 1, "queueCapacity": 12, "power": { "kw": 6 }
}
```

`satisfies[].need` is a **string**, resolved against the need registry. That is the whole answer to
"can a new guest need be added by manifest": yes — a need is declared in a pack
(`needs/thirst.json`: id, decay per hour, weight in the mood mix, icon, thought lines), shops
reference it by id, and the guest module reads the registry rather than an enum.

### Theme (`kind: "theme"`)

A theme is what makes `neon-lagoon` look different without a line of code: palette (fed into
material tinting and into the HUD's accent token), sky/fog profile, water tint and caustic scale,
foliage set, music bed, ambience bed, path styles, prop kit, and a light-rig profile for night.

### Scenario (`kind: "scenario"`)

```json
{
  "id": "cc.first-season", "kind": "scenario",
  "map": "maps/gentle-valley.json",
  "start": { "cash": 250000, "loan": 100000, "date": "03-15", "unlocked": ["cc.*basic*"] },
  "objectives": [
    { "id": "guests",    "type": "guestsAtOnce", "target": 900,  "byDay": 120 },
    { "id": "rating",    "type": "parkRating",   "target": 700,  "byDay": 120 },
    { "id": "solvent",   "type": "neverBankrupt" }
  ],
  "fail": [{ "type": "bankrupt" }, { "type": "ratingBelow", "value": 300, "forDays": 21 }],
  "rules": { "researchSpeed": 1.0, "guestSpawnMultiplier": 1.0, "landPurchasable": true }
}
```

Objective `type`s are registered evaluators — a pack may ship a new one only as a *composition* of
existing predicates (`all`, `any`, `atLeast`, `before`), because arbitrary code in a manifest is a
security decision this game has not made.

## 4. The registry API

```ts
registry.define('flat-ride', def)          // one definition
registry.load(pack)                        // a whole pack, validated
registry.get('flat-ride', 'cc.chair-swing')
registry.all('shop', { category: 'food', unlockedBy: research })
registry.icons(themeId)                    // UI icon set
registry.strings(locale)                   // merged, later packs win
```

Validation is **zod at load time**, and it is strict: an unknown key is an error, not a shrug —
a typo in `capacitiy` that silently becomes `capacity: undefined` is exactly the bug a manifest
format exists to prevent. A failing definition is skipped with a named error; a failing *pack* is
skipped whole. Both surface in the HUD notice tray and in the harness JSON.

Ids are namespaced `<packId-prefix>.<name>`; a collision is an error naming both packs.

---

## 5. What the demo park proves

`demo-park` is a scenario + a set of blueprints in a pack, loaded through this same API. Nothing in
it reaches past the registry into a module. If the demo park can be built from manifests, so can
anybody's.
